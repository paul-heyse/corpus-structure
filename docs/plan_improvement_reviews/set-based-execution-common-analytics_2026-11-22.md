# A common analytical basis for Set-based Execution

**Proposed · 2026-11-22.** Review of the [SBX coordinator](../plans/set-based-execution_2026-11-21.md) and its implementation at `d884fa8a2`, with a clean working tree at inspection. The review follows the annotation fork and scoped relations through publication and selected readback. It also examines selected structural replay, PDF transport, and PostgreSQL integration where those responsibilities affect the choice. It applies the [design principles](../design_review/design_principles/core/design-principles.md), [execution heuristics](../design_review/design_principles/core/efficient-architecture-heuristics.md), and [test assessment](../design_review/design_principles/core/test-assessment.md).

## Judgment

A common analytical basis could remove a material source of SBX implementation burden. Today, several handoffs turn the same population back into tagged JSON, rows, immutable packets, and indexes. When each receiver gets a raw representation, it has to recover the type, scope, or checked facts before using it. A model-derived Arrow projection carried across those handoffs could remove entire reconstruction steps. DuckDB can express containment, dense ordinals, and missing references over that projection. It still takes a query or a construction invariant to establish each of those facts. Arrow's structural validation accepted a test population with a duplicate ordinal and an out-of-range span. One DuckDB query found both. [Pinned-build evidence](../design_review/evidence/2026-11-22_sbx-common-analytics/README.md)

Recommend moving one **end-to-end annotation-fork pilot** ahead of the remaining representation-heavy work and cold-root registration. Keep the plan's empty development cutover and assess the pilot on newly admitted fixtures. Use the pilot to choose a single path for the affected families, including the receivers and readers. Expand SBX-18/19's comparison to include captured DuckDB SQL and PostgreSQL set operations. The strongest immediate Parquet candidate is the frozen selected-review archive in SBX-12. A second operational authority has substantially wider consequences and currently lacks evidence that it simplifies the whole workflow. [Kernel trial](../plans/set-based-execution/kernel-trial.md) · [Empty development cutover](../adr/0150-sbx-empty-development-cutover.md)

## Where the burden comes from

### Annotation fork through publication and selected read

**Inspected.** Source annotations feed two branches. Canonical projection feeds HanLP and declaration interpretation. Primary construction consumes annotations directly with formal evidence. This fork matters because a canonical-only rewrite leaves construction's access to the same source population in place. [Construction roles](../../python/corpus-structure/src/corpus_structure/methods/construction_characterization.py#L205) · [Construction ingress](../../python/corpus-structure/src/corpus_structure/semantic/characterization_ports.py#L741) · [Population plan](../plans/set-based-execution/populations-rules-and-proofs.md#sbx-03)

The partition carrier already shares immutable decoded bodies. Canonical execution materializes the selected projection, thaws it for the CPU call, parses the reply, and acquires the output. Construction acquires nominal members and rebuilds graph inventories and indexes. Acquired annotation and construction inputs already rely on several binding proofs, so the remaining cost includes representation changes as well as validation. The canonical memo preserves local meaning across a rename while rendering the current address at publication. A common schema must carry that distinction between local rows and placement. [Partition carrier](../../python/corpus-structure/src/corpus_structure/semantic/sentence_partitions.py#L100) · [Canonical worker](../../python/corpus-structure/src/corpus_structure/semantic/canonical_sentences.py#L645) · [Construction acquisition](../../python/corpus-structure/src/corpus_structure/semantic/construction_products.py#L1071)

Native admission checks the submitted partition's content and declaration and installs it with the product. A selected read resolves the producing role using exact original bindings and acquires current support and disclosure before accessing the body. An anti-join can establish whether an address resolves *within the supplied relation*. The authority that supplied the relation determines which cut and use that result can speak for. Preserve distinct answers for an absent member and a withheld parent. [Native partition admission](../../python/corpus-structure/src/corpus_structure/semantic/data_operation_partition_native.py#L167) · [Live reference acquisition](../../python/corpus-structure/src/corpus_structure/semantic/live_reference_resolution.py#L50)

### Scoped relations through an artifact consumer

**Inspected.** Scoped relations acquires a source frame, rebuilds construction navigation, acquires formal products, checks predicate contributions, and validates selected passages. The kernel compares pieces with ranges, repeatedly looks up table geometry and navigation, and rebuilds formal inventories for individual formula requests. Joins can answer the prepared range and containment questions together. A window can find the prior row under the same parent with a declared order. Grouping can preserve caption ambiguity. Prepare one formal relation keyed by selected product, projection, pointer, source start, representation, and formal input to replace per-request decoding and scanning. [Scoped ingress and publication](../../python/corpus-structure/src/corpus_structure/semantic/scoped_products.py#L100) · [Scoped kernel](../../python/corpus-structure/src/corpus_structure/methods/scoped_relations.py#L468) · [Formal lookup](../../python/corpus-structure/src/corpus_structure/methods/structural_roles.py#L128)

Report construction still depends on phase order, literal source cues, ambiguity, and canonical contribution identity. The artifact path consumes a nominated contribution through an independently selected report occurrence and checks its actual source. The trial earns its place if it removes the repeated preparation *and* preserves that downstream contract. Moving only the inner range joins leaves those costs and the receiver's representation choices in place. [Artifact consumer](../../python/corpus-structure/src/corpus_structure/semantic/artifact_products.py#L407)

### Which checks earn their place

| Fact | Candidate point of establishment | Consequence for this plan |
|---|---|---|
| Schema, value representation and local shape | Acquire one immutable typed relation under the model projection. Validate external input and any conversion that can change meaning. | Remove repeated decoding, validation and index construction when a downstream component consumes the same admitted projection. Keep canonical encoding at the boundary that requires it. |
| Ordinals, cardinality, containment, inventory closure and coverage | Establish against the complete governing population. Apply window, grouped, or anti-join checks together, or produce the invariant by construction. Carry the premises forward. | Replace repeated per-item work. Group compatible rule evaluations under the same content and rule basis. Keep separately selectable conclusions when consumer scope or admissible provenance differs. |
| Exact occurrence, current selected use, proof eligibility and revocation | Resolve occurrence through the original binding. Acquire a current, purpose-authorized cut from the chosen authority owner. | Batch the lookups and return their admitted projection. Validate authority for the requested use even when the local payload is already resident. |
| Claim, implementation and publication custody | The executing owner authenticates the executable, assets and attempt. The publication owner commits the output, proofs and use outcome together. An immutable captured implementation could change the need for repeated asset checks. | Evaluate a simpler custody mechanism on its own guarantees. The analytical runtime change gives no evidence by itself about late imports, fencing or lost acknowledgements. |

Two earlier costs illustrate the distinction. Detached replay used competing representations of the same completion and repeated recursive schema traversal. Carrying the native-validated completion removed one cause of that work. Native stream tests also refused at installed descriptor correspondence before any kernel ran. Choosing a better analytical engine addresses the first kind of burden more directly than the second. The current CPU verification bracket authenticates mutable implementation premises after successful work admission and after reply collection. ## Recommended amendments

<a id="I01"></a>
### I01. Bring a complete typed-population pilot forward

**Proposed.** Amend [SBX-03 to SBX-05](../plans/set-based-execution/populations-rules-and-proofs.md#sbx-03) and [SBX-08](../plans/set-based-execution/validated-values-and-handoff.md#sbx-08) to compare a model-derived typed projection across annotation → canonical and annotation → construction. Exercise one real selected publication/readback and use canonical → HanLP/declaration for the affected address coverage. Compare the existing immutable carrier, an Arrow projection with DuckDB set steps, and typed PostgreSQL relations with native set checks. Use Arrow compute for direct column transforms where no relational pipeline is needed. Reuse the domain model's declared roles, collections and rule premises when deriving a projection. A schema chosen by a particular engine would introduce another semantic owner. [FP-04 and FP-07](../design_review/design_principles/core/design-principles.md#2-seven-foundational-principles) · [H15, H16 and H19](../design_review/design_principles/core/efficient-architecture-heuristics.md#d-representations-movement-and-live-state)

Use one logical relation per consumer-relevant grain. Carry explicit placement, ordinal, occurrence and presence only where the meaning requires them. Compare in-process Arrow with an owned IPC or Arrow stream if the parent and worker would otherwise serialize the same rows as JSON. This reopens the coordinator's declined Arrow worker packet for the pilot. Test whether the real handoff can avoid that conversion within current byte admission, stop, and cleanup guarantees. Admit at the real trust boundary. Keep canonical value and hash parity through publication and validate the exact current selected use at readback.

Accept the new basis for the affected families if it can remove at least one complete repeated decode/rebuild/validation path without adding another persistent authority or an equally expensive conversion. Require independent expected rows and byte/identity checks where applicable. Compare moved and renamed equal blocks, ambiguous split or merge, duplicate ordinals, containment and missing members, explicit null and absence, and closed-empty versus pending. Include two uses of the same content under different support and a deliberate revocation. Retire the displaced carrier or validation path in the same amendment. If the complete route still rebuilds across every boundary, retain the current carrier and use set execution where it improves the kernel independently.

**Sequence.** Make this placement decision before finishing the remaining representation-heavy migrations and authoring the cold SBX-09 root. Independent implementation custody and native settlement work can proceed in parallel. A chosen replacement still qualifies on an empty current-model installation under the SBX cutover owner. [Cutover sequence](../plans/set-based-execution/cutover-and-qualification.md#development-reset-through-sbx-09)

### I02. Allow captured SQL through the analytical owner

**Proposed.** Reconsider the typed-expression-only constraint in [ADR-0135](../adr/0135-declared-facts-and-typed-database-programs.md) for both DuckDB and PostgreSQL. The DuckDB wrapper already accepts a typed window expression in `select` on the pinned build. Some grouped interfaces and specialised joins can still drive wrapper growth. Trial a maintained, captured DuckDB SQL query for the complete scoped-relations set pipeline against the typed-expression route. Permit reviewed static PostgreSQL SQL at the equivalent owner boundary where it removes generated indirection and the installation pipeline can validate it. Keep each maintained query under one owner and capture its exact definition and versioned dependencies. Use bound values and model-checked input/output shapes. The choice of SQL syntax should preserve parameterization, release correspondence, installed privilege checks, and production observability. [Current analytical owner](../../python/corpus-structure/src/corpus_structure/analytics.py#L28) · [Pinned-build probe](../design_review/evidence/2026-11-22_sbx-common-analytics/README.md)

Use a complete named query with explicit ordering, null behavior, join multiplicities, and tie breaks. For an ASOF match, define what same-position candidates mean before choosing a row. Keep Python text rules and canonical identities wherever the engine diverges. Reconsider the seam for a supported field only after exact positive and negative parity on the pinned route. Reuse the invocation-owned connection as the baseline. Adopt worker-wide reuse when jobs can drain or abort results, release registrations and spill, and isolate the next job after interruption. The probe found an unfinished result actually blocks a second call on the connection. ### I03. Place PostgreSQL work by ownership and test the transfer boundary

**Proposed.** Keep PostgreSQL set operations in the comparison, especially for facts about already admitted rows and for atomic publication. A wider DuckDB candidate should acquire the exact scoped relation from the authority owner and perform worker-local analysis over that finite input. A fully PostgreSQL-native candidate avoids a transfer and can combine the check with publication. It must account for JSON unpacking or typed-row storage, source-local text and formula work, and any return to Python. Select the route that removes more work from the complete operation. [Native admission implementation](../../python/corpus-structure/src/corpus_structure/semantic/data_operation_partition_native.py#L167) · [Scoped Python entry](../../python/corpus-structure/src/corpus_structure/semantic/scoped_products.py#L100)

Compare the current authorized transfer, ADBC, and the DuckDB PostgreSQL extension where each can eliminate material reconstruction. Companion export demonstrates importing the exact exported snapshot into an ADBC transaction and streaming Arrow. Use it as the first integration candidate. Test the DuckDB extension on a private target only if it can consume the purpose-authorized projection and there is a credible benefit over the ADBC route. Inspect actual pushdown and connections used. A test with two related scans and a concurrent change must show one exact cut, correct behavior on revocation, and bounded cancellation and cleanup, or narrow the connector to immutable data. The extension can scan through pooled connections. A read-only attachment answers write permissions while the selected-cut contract needs its own evidence. [Existing ADBC transfer](../../python/corpus-structure/src/corpus_structure/serve/companion_export.py#L125) · [DuckDB PostgreSQL extension](https://duckdb.org/docs/current/core_extensions/postgres/overview) · [Connection pool](https://duckdb.org/docs/current/core_extensions/postgres/connection_pool)

**Architectural alternative.** Assess a DuckDB or DuckLake operational owner explicitly because the authoritative store itself is a choice. The strongest embedded candidate is a single coordinator that owns all writes while workers produce immutable batches. It could remove database deployment and some native-program glue. It would also have to own purpose permissions, attempt fencing, atomic product and proof publication, support selection, revocation, visibility and replay after a crash or lost acknowledgement. Quack and DuckLake offer different multi-process architectures and introduce their own service or catalog. The inspected workflows give a direct reason to change analytical and transfer placement. An operational replacement would need independent evidence of simpler coordination across worker processes, even for one operator. Keep it as a separate architecture proposal if a concrete design can unify those effects. ## Acceptance and coverage

**Tested.** A bounded Linux x86-64 probe used DuckDB 2.0.0 and PyArrow 26.0.0. The SQL cases matched independent expectations for both Arrow and Parquet input. The exact UTC nanosecond sample survived both scans and Arrow output. The CLI showed filter and projection pushdown for the fixture. The probe also showed that the current expression interface can carry a window. These observations establish a build-specific capability and several failure modes. They give no production performance estimate or integrated qualification. [Runnable evidence and limits](../design_review/evidence/2026-11-22_sbx-common-analytics/README.md)

**Proposed.** Use the pilot to count the actual conversions and repeated checks removed along the complete route and to verify which component establishes each surviving guarantee. Prefer independent, deliberately invalid examples and existing real provider and selected-read journeys at the changed boundary. Include Unicode cues, repeated formulas at distinct pointers, phase and tie order, decimals and scope-specific absence for scoped relations. Preserve native authority, provider verification, and interruption tests where they establish different facts. Consider timing or profiling only if conversion, repeated scans, memory or spill could decide between conforming routes. The selected scope excludes broad kernel conversion, the stage deployment, and a complete operational-store migration.
