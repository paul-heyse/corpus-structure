## Coherent target and choices

Start with the developer/operator loop: extend an owned model, inspect its effective contract,
construct a complete product, receive located correction guidance and inspect the exact portable
contract. O01/O02/O04/O09/O11 reinforce that loop. O03 makes archive representation part of the
same explicit ownership rather than another editable model. These are valuable independently
of selecting an ontology or a new execution engine.

O05/O07 enable a second loop: select a vocabulary, explain its membership and meanings, inspect
the effect of a changed snapshot and preserve previous release interpretation. O06 uses those
same inputs to nominate candidates; it must not become an authority for source meaning.
O08 can use recognized units and quantity kinds without depending on broad ontology retrieval.
DDM-11's prepared OAK reuse belongs inside an actual multi-enum preparation operation, not a
standalone cache project. No performance experiment is necessary to justify removing visibly
repeated parsing if the full semantic/lifetime contract is preserved.

O10 can support O09's readable paths and O01's relationship introspection; it does not require
O13 inference. O13 remains a separate, disposable research-view proposition. Shared RDF types
do not make graph conformance, ontology entailment, candidate similarity and scientific support
the same operation. Parameterized constraints are useful only when there is actual shared
semantics; the current two explicit queries are a credible retained alternative.

Prefer existing Pydantic/cattrs mechanisms and prepared products for selected construction and
representation improvements. msgspec/attrs are credible bounded alternatives, not a recommendation
to replace the model substrate. Exact canonical identity, source precision, absence/null,
constructor invariants and archive ABI determine the choice. One semantic authority permits
several operation-shaped representations; it does not require every consumer to rebuild the
same object graph or run the producer again.

## Corrected discovery premises

The review independently corrected DDM-14's proposed missing-outer-contract explanation:
`observations.yaml` already nests StructuralProductReport, ContextualEnrichmentReport,
ArtifactIdentityProduct and SourceContribution. The extra passes bridge representations;
handwritten closure validation also enforces source/citation/variant rules. O04 consequently
investigates normalization locality, not adding a second nested schema.

For DDM-08, complete canonical graph-report bytes are retained in the in-memory GraphValidation
object. The located report exposes a digest; a durable raw-report retrieval route was not
established. O09 must provide actual detail/custody rather than treating a hash as an archive.
Dirty PTD validation v3 adds projection-dependency pages, which are different from subsidiary
JSON errors or graph report details. The discovery remains recoverable unchanged as the input.

## Rule impacts and planning boundary

[D1](../design/D1-knowledge-representation.md), [D2](../design/D2-schema-and-guidelines.md),
[D3](../design/D3-database.md), [D5](../design/D5-consolidation-identity-confidence.md) and
[D8](../design/D8-agent-and-query-interfaces.md) retain authority. Local read-only inspection,
directional construction and diagnostic extensions can build on them. Supporting previously
refused native LinkML relationship, binding, unit or schema-resource constructs requires an
explicit supported-profile decision and faithful affected lowerings; metadata alone is insufficient.

Changing semantic identity, graph entailment, native admission, ordinary publication, process
source policy or archive compatibility requires identifying its actual rule/owner impact and
using the existing ADR/decision route if selected. Current boundaries are not blanket prohibitions
on proposing a better target, and this review does not approve their change. No active plan is
amended, no dependency installed and no database effect authorized by publication.

Subsequent create-plan should select coherent outcomes, preserve the concrete mechanisms and
consumer cases in the companions, and retire superseded paths across affected consumers. A
recommendation can remain conditional until its named feasibility question is settled; neither
documented availability nor a smaller returned object establishes correct or efficient execution.
