# Execution, retention and tools

**Discovery, 2026-11-10; benefits Proposed.** Rich characterization need not mean one pipeline
run, process, persistent object or model per characterized property. Native execution and
interchange can share useful work while preserving distinct observations. This chapter uses
the [shared baseline](briefing.md), source `e283a63`, spaCy3.8.18, en_core_web_sm3.8.0 and
Lark1.3.1; relevant pending discovery text was reassessed. Evidence is current-code, guide,
installed-source and primary-reference inspection on 2026-11-10. No performance, model,
provider or new runtime-compatibility result is claimed.

Installing an extra does not supply trained POS/dependency/semantic models or automatic multilingual interpretation. Select the language implementation and compatible model/resource packages, and assess how its tokenization preserves source/formal atoms. |
| [`Language.set_error_handler`, `TrainablePipe.set_error_handler` / `get_error_handler`](https://spacy.io/api/language#set_error_handler) | **Supporting.** A shared characterization operation can attach component name, affected documents and original exception to diagnostics without collapsing a whole source into an unexplained failure. | No product use was located in the scoped search. Supported components receive the handler; default trainable behavior reraises. It does not roll back already modified documents, establish batch atomicity or safely retry them. Author whether failed outputs are discarded, retained as partial or retried from independently owned input. |
| [`Language.memory_zone()`](https://spacy.io/usage/memory-management#memory-zones) | **Promising-unresolved** for long-lived workers with growing lexical caches. | [`doc_cleaner` / `DocCleaner`](https://spacy.io/usage/memory-management#doc-cleaner), configurable attributes | **Supporting**, especially if transformer-backed Docs are retained. Current [annotate](../../../../python/corpus-structure/src/corpus_structure/ingest/annotations.py) detaches final fields instead of retaining Docs, so immediate benefit is uncertain. Place cleanup after every tensor consumer; representation sharing and cleanup must agree on the last use. |

Configuration is useful here because it exposes the actual composition. It should not grow
into a second application workflow owner. Stable preparation, native batches and a few
meaningful profiles are recommended; independent annotation meanings do not require independent
processes or stored copies. The exact split remains a target-design question.

## Retaining and exchanging the useful result

Current [AnnotationProduct](../../../../python/corpus-structure/src/corpus_structure/ingest/annotations.py)
retains source-bound token columns, availability, component/configuration identity and sentence
ownership. [annotation_view](../../../../python/corpus-structure/src/corpus_structure/ingest/annotation_views.py)
reconstructs a consumer-owned native `Doc` without running a tokenizer/model. Broader annotations
could extend or replace this representation; none of the native formats automatically carries
the repository's source custody, scope, coverage or interpretation contracts.

| Exact capability | Contribution and judgment | Limits, current comparison and remaining authored work |
| --- | --- | --- |
| [`Doc.to_array`, `Doc.from_array`](https://spacy.io/api/doc#to_array) | **Recommended** native numerical access when a consumer wants token columns, graph indices or bulk transforms. It can reduce repeated Python attribute extraction without surrendering annotation meanings. | Arrays contain numeric IDs; strings/vocabulary must remain interpretable. `HEAD` array entries encode relative offsets, whereas `Doc(..., heads=...)` uses absolute token indices. Current [annotation_view](../../../../python/corpus-structure/src/corpus_structure/ingest/annotation_views.py) explicitly preserves the latter. Arrays do not include arbitrary extension objects, group evidence or neural hidden states. |
| [`Doc.to_bytes` / `from_bytes`, `to_disk` / `from_disk`](https://spacy.io/api/doc#to_bytes), [`Language.to_disk` / `from_disk`](https://spacy.io/usage/saving-loading) | **Supporting** native document/pipeline interchange; **Promising-unresolved** as part of a richer retained representation. Document bytes preserve native fields beyond a minimal column projection; pipeline serialization retains configured model/resource state. | Not located as a spaCy document persistence path in product source. Choose exclusions and confirm custom data is serializable. Extension definitions/custom code and external model resources are separate dependencies. A saved `Doc` is not a saved model, nor a complete source-aligned observation contract. |
| [`Doc.to_json(underscore=...)`, `Doc.from_json(validate=...)`](https://spacy.io/api/doc#to_json) | **Supporting** inspectable interoperability for tokens, sentences, entities, categories, named spans and opted-in extensions. Useful for diagnostic or external annotation views. | Installed3.8.18 `doc.pyx` exports span start/end/label/kb_id but omits `SpanGroup.attrs` (including categorizer scores) and span ID. Therefore JSON is not a complete roundtrip for every characterized product. Custom document/token/span extensions are opt-in and must be JSON-serializable; schema validation does not restore omitted evidence. |
| [`DocBin(attrs=..., store_user_data=...)`, `add`, `merge`, `get_docs`](https://spacy.io/api/docbin) | **Recommended** for training/evaluation corpus interchange; **Promising-unresolved** for batches of retained native annotation. Shared strings and selected numerical columns can carry many Docs compactly. | Installed3.8.18 `_serialize.py` also retains categories and serialized span groups; `SpanGroup.to_bytes()` preserves group attributes, including serializable scores. `user_data` is opt-in; extension definitions must still be registered on the reader. It is not random-access analytics storage, and `Doc.tensor`/arbitrary model intermediates are not its corpus contract. |
| [`Span.as_doc`, `Doc.from_docs`](https://spacy.io/api/doc#from_docs) | **Supporting** native subdocument/concatenation operations when selected analysis scopes differ. | Rebased offsets, sentence ownership, shared vocabulary and excluded fields need explicit mappings. Group-level evidence and discontinuous source pieces must be preserved deliberately. No inspected current source used these methods; [source-bound layout and views](../../../../python/corpus-structure/src/corpus_structure/ingest/annotation_views.py) already protect an exact block contract. Avoid treating concatenated text as one original contiguous source. |
| [Lark positioned tokens/trees and explicit serialization](https://lark-parser.readthedocs.io/en/stable/classes.html#tree) | **Recommended** retention of recognized structure and alternatives with original positions. Current [math/native.py](../../../../python/corpus-structure/src/corpus_structure/methods/math/native.py) explicitly serializes token/node extents for later normalization without recognition. | Native `Tree.copy()` omits root metadata and shares children; Token deep-copy/pickle omits end positions in1.3.1. Neither parser serialization nor a generic object copy replaces an authored result contract. Details and richer AST/forest choices belong in [representation/composition](representations-and-composition.md). |

## Grammar preparation, diagnostics and deployment

| Exact capability and current integration | Contribution and judgment | Prerequisites and remaining authored work |
| --- | --- | --- |
| [`Lark.open`, `Lark.open_from_package`, `import_paths`, `source_path`, `get_terminal`](https://lark-parser.readthedocs.io/en/stable/classes.html#lark) | **Recommended** resource-based grammar families and compiled-terminal inspection. Shared quantity/reference/formal grammars can remain named reusable resources rather than embedded copies. | Current [math/grammar.py](../../../../python/corpus-structure/src/corpus_structure/methods/math/grammar.py) assembles shipped SymPy grammar plus local extensions; [structural_parsing.py](../../../../python/corpus-structure/src/corpus_structure/semantic/structural_parsing.py) embeds smaller cached grammars. Author family/import ownership and semantic callbacks; `get_terminal(name).pattern.to_regexp()` can explain actual boundaries after composition. |
| [`cache=True` / `cache="path"`, `cache_grammar=True`](https://github.com/lark-parser/lark/blob/1.3.1/lark/lark.py) | **Supporting** reuse of LALR grammar analysis across constructions/process starts. `cache_grammar` additionally retains the unanalyzed grammar for facilities such as reconstruction. | LALR only. Current per-process [field grammar caches](../../../../python/corpus-structure/src/corpus_structure/semantic/structural_parsing.py) already amortize preparation; current mathematical Earley parsers cannot use this cache. Callable transformer/postlex/lexer callbacks/edit-terminal/plugin objects are excluded from cache hashing; maintain explicit configuration/code identity. It does not speed an already-constructed parser's recognition algorithm. |
| [`Lark.save`, `Lark.load`](https://github.com/lark-parser/lark/blob/1.3.1/lark/lark.py) | **Supporting** prepared LALR artifacts where repeated startup or distribution makes them worthwhile. | `save()` rejects non-LALR parsers in1.3.1. Pickle-backed parser artifacts require trusted provenance and release/Python compatibility. Author artifact invalidation and callback availability. Shipping prepared tables is not a richer characterization feature and does not replace retaining recognition results. |
| [`lark.tools.standalone`, `--compress`](https://github.com/lark-parser/lark/blob/1.3.1/lark/tools/standalone.py) | **Supporting** for a fixed deterministic grammar delivered independently; **Not advantageous** as a default replacement for the current runtime grammar composition. Generated LALR modules trade configurable runtime grammar construction for regeneration. | Compression embeds pickle/zlib/Base64 parser data and changes artifact size/startup, not accepted language. Reduced API, fixed grammar and regeneration must fit the consumer. It retains interactive LALR code but does not deliver current Earley alternatives or arbitrary Python-side parity. |
| [`strict=True`, `debug=True`, optional `interegular`](https://lark-parser.readthedocs.io/en/stable/how_to_use.html#strict-mode) | **Recommended** LALR grammar-authoring diagnostics as deterministic characterization families expand. Strict mode raises for shift/reduce conflicts and supported terminal regex collisions. | Collision analysis needs interegular, absent from inherited metadata; some regex constructs cannot be analyzed. Do not present strictness as proof of semantic correctness, exhaustive grammar coverage or absence of every lexical ambiguity. No new alignment lint/check is proposed. |
| [`UnexpectedCharacters`, `UnexpectedToken`, `UnexpectedEOF`, `UnexpectedInput.get_context`, `match_examples`, `VisitError.orig_exc`](https://lark-parser.readthedocs.io/en/stable/classes.html#unexpectedinput) | **Recommended** distinct recognition/transformation failure characterization. Preserve what was recognized, where grammar acceptance failed and whether semantic conversion failed later. | Current [math/grammar.py](../../../../python/corpus-structure/src/corpus_structure/methods/math/grammar.py) categorizes exceptions/TeX tokens and applies bounded punctuation retry; it explicitly does not use `match_examples`. The latter compares authored invalid examples, not arbitrary meanings. LALR early end may appear as an unexpected `$END` token. Author domain diagnostic labels and retain original failed input. |
| [`parse_interactive`, `feed_token`, `feed_eof`, `accepts`, `choices`, `copy`, `as_immutable`, `resume_parse`](https://lark-parser.readthedocs.io/en/stable/classes.html#interactiveparser) | **Promising-unresolved** for typed-token composition, inspecting candidate syntax continuations and branching controlled constructions. These primitives can consume earlier characterized units. | LALR only; current math is Earley. An accepted terminal name is not a complete meaningful suggestion. This is token advancement/state branching, not edit-aware incremental document reparsing. Source mapping for fed tokens and candidate branches remains authored. |
| [`Lark.parse(..., on_error=callback)`](https://github.com/lark-parser/lark/blob/1.3.1/examples/advanced/error_handling.py) | **Promising-unresolved** for retaining explicitly repaired interpretations of noisy/OCR-like formal fragments. A callback can inspect parser state, insert tokens or skip offending input and request continuation. | LALR recovery, not a repair policy supplied by the library. Preserve original input, inserted/deleted pieces and repaired status; grammatical acceptance after repair does not establish source truth. Current punctuation retry is a different bounded policy. Compare retaining an unrepaired diagnostic plus independent lexical units with authoring a repair grammar. |
| [`regex=True`, `lark[regex]`; `lark[atomic-cache]`](https://pypi.org/project/lark/1.3.1/) | `regex` is **Supporting** for Unicode/property-aware lexical recognition; **Supporting** cache-handling extra when a selected cache route needs it. | Neither supplies language grammar, terminology, semantic normalization or a new parsing algorithm. Select regex capabilities by actual terminal needs; grammar/cache ownership is still authored. Lexical details are assessed in [segmentation](segmentation-and-lexical-analysis.md). |
| [`lark-cython` `_plugins`](https://github.com/lark-parser/lark_cython) | **Supporting**, with unresolved workload benefit. Accelerated LALR lexing/parsing could matter after selecting useful deterministic grammar families. | Separate compatibility contract: documented tokens do not subclass `str` and postlex is unsupported. No current product plugin use was located; the mathematical Earley route is not its acceleration target. Do not import upstream benchmark gains into this workload or make speed a prerequisite for recognizing functional grammar value. |

The preparation judgment is selective: retain the useful current lazy parser/model/matcher
owners, and expand them when a richer grammar family needs shared preparation. The first-layer
target does not require a serialized parser artifact, generated standalone module or recovery
path for every grammar. Conversely, no current deployment need is required to identify their
conditional functionality.

**not_run**. The coordinator owns assembled publication checks. Proposed benefits here are
functional composition and less repeated preparation/translation; no quantified gain follows.
