# Segmentation and lexical analysis

**Proposed discovery judgments, 2026-11-10.** Objective: expose the richest useful primary
characterization of text, including technical prose, rather than limit analysis to existing
extraction recipes. Read against baseline `e283a63c09c8881698a51495c9dbe48f757b44f3` and the
pending discovery revisions that this topic account replaces. The selected project declares
spaCy **3.8.18**, `en_core_web_sm` **3.8.0** and Lark **1.3.1**; the prepared root Python 3.14
environment contains spaCy/Lark distribution metadata and release sources at those versions.
Source/reference inspection establishes capability, not annotation accuracy or runtime results.
[Family scope](briefing.md) owns the shared discovery boundary. Version-sensitive observations
also use installed `spacy/pipeline/{dep_parser.pyx,attributeruler.py,lemmatizer.py}` and
`lark/{lark.py,lexer.py,parser_frontends.py,indenter.py}` beneath
`.venv/lib/python3.14/site-packages/`. The attempted upstream spaCy `v3.8.18` source URL
returned HTTP 404 on 2026-11-10; live official APIs and installed source are distinguished here.

The strongest direction is a common positioned token/sentence foundation with lexical,
morphological and syntactic annotations, alongside grammar-based lexical views for structured
fragments. Different views need not force one tokenization onto all analyses. spaCy supplies
language-aware prose segmentation; Lark supplies declared terminal vocabularies and grammar-aware
lexical decisions. Neither library by itself recovers lost PDF layout or supplies universal
multilingual interpretation.

## Prose boundaries and technical atoms

| Feature and exact mechanism | Structural contribution and judgment | Conditions and authored remainder |
| --- | --- | --- |
| spaCy language tokenizer: `Tokenizer`, language `Defaults`, special-case rules, prefix/suffix/infix searches | **Recommended:** retain recognizable technical words, punctuation and abbreviations as positioned units, preserving whitespace and original text. [Tokenization](https://spacy.io/usage/linguistic-features#tokenization), [Tokenizer](https://spacy.io/api/tokenizer). | Rules and trained models are separate. Technical exceptions remain authored; changing rules can change all downstream token indices. Existing [atom-preserving layout](../../../../python/corpus-structure/src/corpus_structure/ingest/sentences.py) already supplies a suitable source boundary, not the full lexical target. |
| `token_match`, `url_match`, `add_special_case()`, tokenizer factory; `Tokenizer.explain()` | **Recommended:** discriminate identifiers, URLs and notation that should remain whole; explain which rule produced a boundary. [Customization](https://spacy.io/usage/linguistic-features#tokenization), [API](https://spacy.io/api/tokenizer). | `token_match` and URL handling have different positions in tokenization. Matchers must return matches under the documented callable contract. Replacing the entire tokenizer is **Supporting**, preferable only when rules cannot express the desired population. |
| `Doc(vocab, words=..., spaces=...)`, `Token.idx`, `Span.start_char/end_char`, `Doc.char_span()` | **Recommended:** ingest already delimited prose/math/reference atoms without rewriting source characters; connect external extents to tokens. [Doc](https://spacy.io/api/doc). | `strict` rejects misaligned boundaries; `contract` excludes partial tokens; `expand` includes them. Preserve the original character extent separately when snapping. Boolean `spaces` alone cannot encode arbitrary whitespace: the existing layout also retains whitespace tokens and checks exact reconstruction. |
| `Doc.retokenize().merge()` / `.split()`; training `Alignment` | **Supporting:** correct boundaries and relate alternate tokenizations rather than manually repairing dependency columns. [Retokenization](https://spacy.io/api/doc#retokenize), [Alignment](https://spacy.io/api/alignment). | Apply before publishing token-bound products or regenerate affected annotations. Alignment is not an arbitrary source-coordinate mapping. Current [restored views](../../../../python/corpus-structure/src/corpus_structure/ingest/annotation_views.py) deliberately reject changed token populations. |
| `parser` sentence breaks, respecting preset `Token.is_sent_start` | **Recommended** for rich characterization: one parse provides syntax and sentence boundaries; preset boundaries preserve math/reference restrictions. [DependencyParser](https://spacy.io/api/dependencyparser). | A model is required. Boundaries are predictions, and incorrect hard constraints can suppress correct splits. The existing [sentence producer](../../../../python/corpus-structure/src/corpus_structure/ingest/sentences.py) constrains blocks/atoms; assess any broader sentence unit against native block ownership. |
| `senter` / `SentenceRecognizer`, `overwrite` | **Supporting:** learned sentence-only alternative when syntax is deliberately omitted. [SentenceRecognizer](https://spacy.io/api/sentencerecognizer). | Requires trained weights; availability in a package does not imply it is active. `overwrite=False` preserves existing boundaries. It is **Not advantageous** as an additional independent mandatory pass when the same input already needs parser syntax. |
| `sentencizer`, `punct_chars`, `overwrite`; custom boundary component before parser | **Supporting:** deterministic punctuation or document-specific boundaries without learned parsing. [Sentencizer](https://spacy.io/api/sentencizer), [sentence segmentation](https://spacy.io/usage/linguistic-features#sbd). | Punctuation inventories and nonpunctuation boundaries require authoring. Use custom components for known source conventions; do not present punctuation rules as equivalent prose understanding. |
| `DependencyParser(learn_tokens=True)` | **Promising-unresolved:** experimental learned merging of oversegmented subtokens could improve noisy/technical text segmentation jointly with syntax. [API](https://spacy.io/api/dependencyparser). | Defaults to false; training/tokenization alignment and downstream population changes matter. This is learned merging, not a general learned tokenizer or splitting mechanism. Next question: are relevant boundaries better handled by stable exceptions or by a separately qualified merging model? |

## Lexical, grammatical and normalized token attributes

| Feature and exact mechanism | Structural contribution and judgment | Conditions and authored remainder |
| --- | --- | --- |
| `Lexeme` / `Token` flags: `is_alpha`, `is_digit`, `like_num`, `like_url`, `like_email`, `is_punct`, `is_quote`, `is_bracket`, `is_space`, `is_stop`; `shape_`, `lower_`, `norm_`, prefix/suffix | **Recommended:** reusable lexical classes and surface variants alongside exact source spelling. [Lexeme](https://spacy.io/api/lexeme), [Token](https://spacy.io/api/token). | Lexical heuristics are not semantic types: `like_num` does not establish a parsed number; stop-word status does not authorize removing a token. Language defaults and domain exceptions remain explicit. |
| `tagger` → `Token.tag`; `morphologizer` → `Token.pos` / `Token.morph`; `MorphAnalysis.get()` | **Recommended:** distinguish fine tags, grammatical category, tense, person, number, mood and other available features for sentence interpretations. [Tagger](https://spacy.io/api/tagger), [Morphologizer](https://spacy.io/api/morphologizer), [MorphAnalysis](https://spacy.io/api/morphanalysis). | Model/language inventories differ. English selected here uses tagger plus attribute mapping; a morphologizer is an alternative architecture, not an automatically useful additional predictor. Morphologizer `overwrite`/`extend` govern interaction with earlier features. Preserve missing versus available features. |
| `AttributeRuler.add(patterns, attrs, index=...)`, `add_patterns()`, tag/morph mapping loaders | **Recommended:** contextual token annotation for technical senses or exceptional POS/lemma/morphology, including selecting a token with a negative index in a multi-token match. [AttributeRuler](https://spacy.io/api/attributeruler). | This mutates supported token attributes; rule order and pipeline placement matter. Use parallel annotations for competing readings rather than overwriting one with another. Mapping/correction rules remain authored. |
| `lemmatizer`, `mode="lookup"` or `"rule"`; language-specific POS-conditioned modes | **Recommended:** retain lemma separately from surface form for recurring predicates, nominalizations and terminology. [Lemmatizer](https://spacy.io/api/lemmatizer). | Lookup uses tables; rule mode generally needs upstream POS. POS-conditioned lookup is language-specific, not a universally selectable third core mode. `overwrite=False` respects existing lemmas. The richer [annotation profile](../../../../python/corpus-structure/src/corpus_structure/ingest/annotations.py) enables lemmatization whereas sentence-only configuration excludes it. |
| `trainable_lemmatizer` / `EditTreeLemmatizer` | **Promising-unresolved:** predict edit-tree transformations where dictionary/rule coverage is poor, including technical inflection. [EditTreeLemmatizer](https://spacy.io/api/edittreelemmatizer). | A model must be initialized/trained; installation does not supply domain predictions. Research value exists before a dataset does. Next question: do recurring unseen forms need learned edits, or do lookup exceptions provide the desired distinctions more transparently? |
| `Vocab`, `StringStore`, language `lex_attr_getters`, `Lookups` | **Supporting:** share lexical state, string identities and language/domain dictionaries across token views. [Vocab](https://spacy.io/api/vocab), [Lookups](https://spacy.io/api/lookups). | Hashes require the associated string store for readable recovery. Lexical values are type-level; context-dependent interpretation belongs on tokens/spans, not a shared lexeme. |

## Grammar-defined lexical views

| Feature and exact mechanism | Structural contribution and judgment | Conditions and authored remainder |
| --- | --- | --- |
| Lark `parser=None, lexer="basic"`, `Lark.lex()` | **Recommended:** a positioned terminal vocabulary for technical symbols, identifiers, comparators, codes and other formal fragments, reusable without syntax parsing. [Lark API](https://lark-parser.readthedocs.io/en/stable/classes.html#lark.Lark.lex), [1.3.1 lexer-only compilation](https://github.com/lark-parser/lark/blob/1.3.1/lark/lark.py). | Explicit basic lexer is necessary; `auto` has no lexer-only branch in 1.3.1. All declared terminals survive this mode. Existing [field lexer](../../../../python/corpus-structure/src/corpus_structure/semantic/structural_parsing.py) demonstrates the mechanism; useful vocabularies extend well beyond numbers. |
| `basic` versus LALR `contextual` | **Recommended:** basic for context-independent lexical inventories; contextual when the surrounding grammar should decide whether text is a keyword, label or identifier. [Parsers](https://lark-parser.readthedocs.io/en/stable/parsers.html), [1.3.1 lexer](https://github.com/lark-parser/lark/blob/1.3.1/lark/lexer.py). | Contextual limits candidates to the parser state's accepted terminals. It does not expose every lexical reading or make an ambiguous grammar deterministic. `Lark.lex()` does not reproduce those state-dependent choices. |
| Earley `dynamic` versus `dynamic_complete` | **Promising-unresolved:** retain competing terminal types and, with `dynamic_complete`, shorter regex matches when token boundaries are themselves interpretive alternatives. [Parser options](https://lark-parser.readthedocs.io/en/stable/parsers.html), [dynamic-complete example](https://lark-parser.readthedocs.io/en/stable/examples/advanced/dynamic_complete.html). | Ordinary dynamic uses longest matches per terminal; complete exploration can amplify broad terminals heavily. Prefer structured rules over catch-all regexes. Next question: which ambiguous boundaries change a useful sentence interpretation? |
| Terminal strings/ranges/regexes, flags, numeric priorities; `g_regex_flags`, `regex=True`; `unicode.lark` | **Recommended:** explicit lexical alphabets, Unicode categories and controlled collisions for notation and multilingual identifiers. [Grammar](https://lark-parser.readthedocs.io/en/stable/grammar.html#terminals), [Unicode example](https://lark-parser.readthedocs.io/en/stable/classes.html#using-unicode-character-classes-with-regex), [shipped grammar](https://github.com/lark-parser/lark/blob/1.3.1/lark/grammars/unicode.lark). | Basic/contextual precedence uses priority, theoretical match length, definition length, then name. Unicode property regexes require the optional `regex` engine; Unicode support is not language morphology. Terminal priority chooses an analysis rather than proving it correct. |
| `lexer_callbacks`, `Token.update()`, `Token.new_borrow_pos()` | **Supporting:** lexical normalization or collection of ignored comments/trivia with retained original coordinates. [Callbacks](https://lark-parser.readthedocs.io/en/stable/examples/advanced/conf_lalr.html), [1.3.1 Token source](https://github.com/lark-parser/lark/blob/1.3.1/lark/lexer.py). | Callbacks apply to basic/contextual lexing. Borrowed positions describe original text, not the replacement string's length. Normalization policy remains authored; keep exact surface spelling separately. |
| `%ignore`, `lex(dont_ignore=True)`, `keep_all_tokens` | **Recommended:** distinguish syntactically irrelevant material from source material that still matters to characterization. [Grammar ignore](https://lark-parser.readthedocs.io/en/stable/grammar.html#ignore), [1.3.1 lex implementation](https://github.com/lark-parser/lark/blob/1.3.1/lark/lark.py). | `dont_ignore=True` reveals ignored tokens during standalone lexing; `keep_all_tokens` affects tree filtering and does not undo `%ignore`. Ignored directives are not imported with grammar modules. Trivia-to-node association remains authored. |
| Custom `Lexer` class, arbitrary input objects, `%declare` terminals; `InteractiveParser.feed_token()` | **Promising-unresolved:** parse typed spaCy units or native math/reference atoms without converting every distinction back to text regexes. [Custom lexer](https://lark-parser.readthedocs.io/en/stable/examples/advanced/custom_lexer.html), [1.3.1 input restoration](https://github.com/lark-parser/lark/releases/tag/1.3.1). | Mapping, position and token-type policy remain authored; parser/lexer combinations must be selected deliberately. Custom input support was restored in 1.3.1. Interactive feeding is LALR-specific, not generic incremental reparsing. Compare a typed-token grammar with direct dependency matching for each construction. |
| `postlex.process()`, `postlex.always_accept`, `edit_terminals`, `get_terminal()` | **Supporting:** inject/transform lexical units, preserve globally needed tokens, specialize terminal definitions and inspect compiled patterns. [1.3.1 options](https://github.com/lark-parser/lark/blob/1.3.1/lark/lark.py), [contextual wiring](https://github.com/lark-parser/lark/blob/1.3.1/lark/parser_frontends.py). | `always_accept` affects terminal retention and contextual visibility. Postlex is incompatible with dynamic lexing; Earley plus auto plus postlex selects basic. Pin lexer choice to avoid accidentally losing lexical alternatives. Compiled terminal inspection alone cannot explain parser-state decisions. |
| `Indenter`, `PythonIndenter`, newline/bracket token types, tab width | **Supporting:** turn genuine indentation into structural tokens for outlines, pseudocode and formal examples. [Indentation example](https://lark-parser.readthedocs.io/en/stable/examples/indented_tree.html), [1.3.1 source](https://github.com/lark-parser/lark/blob/1.3.1/lark/indenter.py). | Requires newlines containing following indentation; bracket nesting suppresses indentation tokens. Comments and blank lines must be handled by the grammar. **Not advantageous** for inferring PDF hierarchy from reflowed prose: absent geometry cannot be recovered by this postlexer. |
| `TextSlice`, `use_bytes=True` | **Supporting:** analyze a source region while retaining document coordinates; bytes only where input is truly byte-oriented. [TextSlice](https://lark-parser.readthedocs.io/en/stable/classes.html#textslice). | TextSlice is basic/contextual only and computes initial line/column from the prefix; it is not constant-time setup. Bytes impose ASCII-compatible grammar restrictions and require an explicit byte/character coordinate conversion for repository text. |

## Selection and remaining questions

**Recommended target:** retain surface units and their native atom roles, make full lexical and
morphological characterization available with clear component/model provenance, and compose
grammar lexical views where they reveal additional structure. The sentence-only route remains
useful for boundary-only demand, but does not define the ceiling of the primary text product.
This judgment follows FP-03/04's scoped semantic authority and H4/H12/H15: delegate established
segmentation/annotation mechanisms, share stable preparation, and preserve different physical
views where their semantics differ. No numerical performance benefit is claimed.

The consequential open choices are the desired token population for noisy/technical prose,
which lemma/morphology alternatives merit learned components, and whether uncertain lexical
boundaries need correlated alternatives. Existing models or rules can be assessed first; a new
training dataset is a possible realization cost, not a prerequisite to recognizing value.
Sentence grammar and interpretation are assessed in
[sentence structure](sentence-structure-and-interpretation.md); the [family briefing](briefing.md)
routes language/layout alternatives; [composition](representations-and-composition.md) and
[models](models-supervision-and-evaluation.md) assess representation and model lifecycle.
