# Regeneration, retirement and integrated acceptance

**Status:** Planned · **Created:** 2026-10-29 · **Proposed.** [Coordinator](../semantic-model-pivot_2026-10-29.md) owns current state and combined completion. This document owns integration journeys and qualification boundaries for O01–O06.

## Adoption boundary

Clean regeneration replaces the current runtime interpretation through a fresh realization. It does not migrate old runs, preserve key scheme 1, install legacy upcasters or dual-write knowledge. Existing plans/evidence and unrelated dirty work remain intact. Creating a fresh owned database on PostgreSQL `18/corpus` is distinct from disposing of an old database; no deletion scope is implied. Other projects' clusters, including main port 5432, are untouched.

The same current entry points use the new semantic contracts after cutover. Do not claim completion while old admitted writers/readers remain reachable as alternate authority. Useful pure algorithms and source/evidence processing stay; remove replaced model projections, dispatch paths, unsafe raw writes and obsolete tests together with their replacements. Historical artifacts can remain recoverable in Git without forcing runtime compatibility.

## SP-09 — Regenerate and retire replaced paths

**Input:** working SP-05–SP-08 integrations, decisions and physical bootstrap. **Owner:** root integration with consumer owners.

Create a reproducible command path that prepares a release, bootstraps a fresh realization, ingests actual source documents, performs configured extraction, consolidates/derives, serves evidence-backed answers and evaluates independent references. Record the source and release dependencies. Regeneration must not read pre-pivot knowledge rows; fixture insertion or schema generation alone does not establish the product workflow.

Run the statistics trace and a small ownership/inspection transfer fixture. The latter exercises attributed/time-qualified relations, repeated occurrences, quantity/unit and a nested/n-ary construct without expanding the production corpus roadmap. Use current native providers required by the supported path; report unavailable providers as open prerequisites, not mocked passes. Deterministic component fixtures remain useful independently.

Move CLI/MCP/run defaults to the new realization only after the required working inputs exist. Keep the old realization untouched as an external reference until disposal is explicitly scoped. If preparation/publication fails, no partial data becomes the selected realization. Interruption before cutover leaves the current default intact; restart uses release/batch identities rather than manufacturing new occurrences. No general hot-upgrade or recovery framework is needed for this single-operator replacement.

Review the complete consumer inventory from SP-06/SP-08, remove superseded production routes and update enduring contracts in existing architectural owners through the scheduled decision work. Do not edit old plan scope or transfer its finding statuses as a side effect. Any later old-plan reconciliation is separate work.

**Completion:** actual source-to-answer regeneration under the new model, current entry points routed consistently, named retired paths no longer reachable, and records of source/release/data context. Required but unavailable obligations remain open. SP-09 is functional integration, not full qualification.

## SP-10 — Final source qualification

**Input:** SP-09 complete functional scope and final maintenance source. **Owner:** root assembled-tree acceptance.

During implementation run targeted functional checks for coherent packages. At complete scope, run `just turn-end`, preserving unrelated concurrent work and inspecting incidental formatting effects; then applicable native journeys and `just test-all`, followed by applicable `just hygiene`. Fix scope-owned failures and re-run the affected check. Reassess evidence affected by subsequent source/harness/environment changes. Maintenance recipe success is not equivalent to clean lint or product qualification.

Acceptance covers the required union below. Reuse native tests and shared production validators for consumer checks; expectations challenging a validator/model remain independent. Do not add a new alignment gate, evidence framework or mandatory benchmark campaign. Existing evidence conventions retain failed/interrupted receipts; new probes belong in the established evidence folder only when they resolve a real uncertainty.

| Required behavior | Evidence capable of exposing an incorrect implementation |
|---|---|
| Dynamic class, attribute and relationship | Native declaration → agent/schema → observation → publication → query/explain with no per-type DDL/code; compare physical schema before/after |
| Occurrence, fact and conflict scope | Independent expected sets for same-source duplicate items, two supporting sources, disagreeing accepted-value candidates and retry identity |
| Formal ontology/release authority | Pinned local artifacts, membership/hierarchy/mapping expectations; unsupported/unavailable/unchecked distinctions; old bound operation unaffected by activation |
| Strong publication | Real SERIALIZABLE races, COPY failures, cross-scope references, direct-DML denial, secure routine resolution, rollback and ambiguous-commit replay |
| Exact structured values | Independent decimals/units/missingness at projection limits, nested references, role ordering and multiplicity across SQL/Arrow/DuckDB/RDF |
| Qualified inference | Positive eligible closure, negative-premise non-inference, incompatible contexts, cycles and multiple supports without unbounded proof expansion |
| All consumers and reproducibility | Actual CLI/MCP/query/export/intervention/evaluation paths; release-sensitive reuse and continuation; evidence closure and gold isolation |
| Execution and resource behavior | Narrow Core access paths for selective queries, sufficient global context, honest partial outcomes, stream cancellation and connection/registration release |
| Physical evolution | Fresh bootstrap and controlled physical revision; reviewed SQL/routine deployment; equivalent semantic result before/after a derived optimization |
| Clean regeneration | Actual source workflows for statistics plus transfer fixture, with no legacy knowledge reads |

Quantitative performance measurements are deferred unless a concrete capacity/access-path uncertainty requires them. Qualitative assessment still addresses skew, global constraints, intermediate growth and retained resources. Limits/refusal alone do not establish workload fit.

**Completion:** required native evidence covers final source/context; `just test-all` and applicable `just hygiene` pass for that tree; unavailable required obligations remain open. Record `passed`, `failed`, `blocked` with missing prerequisite, or `not_run` and exact commands. Do not claim a completion audit unless separately performed through its skill.
