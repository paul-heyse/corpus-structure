## Change and revocation algorithm

1. Pin old/new definition revisions, requested subject/discovery universe, selected result bindings
   and trust snapshot. Compare effective semantic contract/recipe/eligibility projections.
2. Find directly affected definitions and newly applicable or never-derived subjects using both
   old/new declared relations. Include population additions/removals, reordered input and optional
   presence/absence changes, not only rows with existing derivations.
3. Follow indexed reverse input/support lineage within relevant demand scope. Classify potential
   impact, awaiting upstream determination, incompatible/stale selected binding, revoked support,
   currently substitutable, inapplicable or unknown. Record reasons and exact reference witnesses.
4. Execute changed requested producers only through demand execution. When new value/support is
   substitutable, stop propagation. A transitive consumer is not proven stale merely because an
   upstream declaration changed.

Eligibility-only widening preserves prior recipes only when result scope, coverage, inputs, effects
and validity cannot change. Output schema equality alone does not prove compatibility. Cross-release
admission also checks original source/context/custody, outcome strength, selected alternatives,
purpose permissions and trust. Meaning-changing translation is a named admitted operation.

Revocation appends a scoped reason/selector under DDO-04's trust epoch protocol. It invalidates
required support paths, not raw shared content. Supported target-basis selections stay immutable; this does not require an interpreter for obsolete encodings. Another
support path is usable only when explicitly admitted by the consumer contract; recomputation after
revocation appends a new derivation generation. Retry, revocation and requested replicate remain
different operations. Serving an old snapshot is distinct from assessing its current trust.

## Validity and change-triggered readiness — production-efficiency · 2026-11-17

**Accepted scope; implementation Proposed.** The coordinator owns status; the
[integration companion](production-efficiency-integration.md) owns slice order. The products
companion owns the native contract; this section states what it means for currentness.

- **One validity definition (PE-S18).** Currentness and substitutability keep one mechanism.
  Set-wise evaluation changes how validity is computed, not what it means: an episode's direct
  validity, population supersession, original visibility and the value-substitution rule are
  the same predicates, evaluated once per distinct node per statement. No maintained
  invalidation record is introduced, so revocation and impact keep a single authority.
- **Invalidation causes.** Revocation is append-only and always current. Supersession and
  original visibility are relative to the read boundary. A native kernel change invalidates
  kernel-checked families through the lowered release digest. These three are the only causes;
  an obligation's readiness otherwise only grows.
- **Change-triggered readiness (PE-S26).** A waiting obligation is re-bound only when its
  `inputs_watermark` advances, that is when a prerequisite publication, population or original
  becomes visible. This is the "propagate relevant change, not touch" rule applied to the
  frontier. It never suppresses a re-check after an invalidating event: invalidation is
  evaluated by validity at attach and at every settlement, not by the watermark.
- **Reverse impact.** Reverse-lineage indexes are added with the first reverse-impact consumer
  in DDO-09, not before.
