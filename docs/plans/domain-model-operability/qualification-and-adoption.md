## Supported behavior and evidence boundary

A useful result has declared inputs, authentic production and publication, the required current
authority, and a readback that exposes the selected output. Admission, executable acquisition,
provider execution, publication and selected readback each establish a different property. The
qualification reports those properties individually, including a failure after successful
publication. An operator should be able to find the first failed prerequisite through the existing
managed inspection commands.

Required evidence covers ordinary functional behavior, exclusive fault behavior, actual providers,
repository checks and the whole-book journey. One qualifying run can satisfy several properties
where its actual source, context and scope cover them. Retain failed and interrupted attempts.
Commands report `passed`, `failed`, `blocked` with the missing prerequisite, or `not_run`. A provider
stub supplies controlled contract evidence. An actual provider receipt supplies provider evidence.
Both must retain the assertion and publication scope they established.

All planned checks below are `not_run` at authoring. No product test, database operation or provider
call was performed to write this plan. Numerical speed targets and exhaustive semantic agreement
with generated historical outputs are outside the acceptance design. Semantic examples use useful
independent expectations and reveal the specific distinctions the target must preserve.
