## Intended behavior and baseline

Native enforcement continues to protect independent writers, privileges, identity, locking and
atomic publication. Future desired native objects are authored through model-derived relational
and structured PostgreSQL products wherever their complete contracts can be preserved. SQL
emitted for deployment is a derived artifact; moving maintained SQL into a template, annotation
or compiler callback does not eliminate its authoring burden.

**Planning baseline, inspected at `370f0643`:** `semantic/native_products.py:91–131` generates
physical tables/indexes/FKs with Core; `:389–530` compares selected CHECK bodies and UNIQUE
columns. `semantic/alembic_native.py:21–187` supplies genuine Plugin/comparator/operation/renderer
integration, explicit recreation and catalog checks. `native_objects.py:98–186` still receives
SQL definitions; `NativeObject.statements` contains strings. `native_inventory.py:20–26` requires
one string `AS` body, and `native_objects.py:311–314` rejects observed SQL-standard bodies.
These describe the planning baseline, superseded for the selected scope by the execution checkpoint
below; they are not a claim that native bodies are semantically inert.
Source paths are relative to `python/corpus-structure/src/corpus_structure/`.

Native body/custody seams describe the inspected snapshot. The PDF/native/model series remains
in progress and may change these seams. A later discrete update will reconcile its landed state;
this plan does not chase ongoing edits or absorb PDF completion, provider/default adoption or
other unfinished obligations. Preserve concurrent work and do not assume deployment complete.

## Selected authoring and custody design

Use Core schema/DDL for supported Table/Constraint/Index/CreateView forms, and pglast nodes for
missing PostgreSQL declarations and suitable SQL-language body construction. Keep desired object
identity, input/output signature, owner, privileges, safe settings, volatility/strictness/parallel
properties and dependencies explicit. Trusted implementation programs supply algorithmic meaning;
the model binds their contract/version instead of claiming that descriptive effect text is code.

A normalized native authoring product distinguishes a string body from a structured SQL-standard
body and records the exact generated deployment bytes plus a versioned comparison recipe.
For structured bodies, identity must account for PostgreSQL-resolved dependencies and relevant
catalog properties, not a digest of an absent `AS` option or a generic AST fingerprint.
Exact generated bytes remain custody evidence; body equivalence is limited to the declared
normalization/profile, not a general semantic-equivalence claim.

Existing source acquisition, desired/predecessor comparison and admission owners are extended;
no new migration engine or writable shadow catalog is introduced. Old frozen revisions retain
their reader and byte contract. New authoring does not rewrite historical SQL.

Pglast `parse_plpgsql()` returns dictionary/list structures rather than the typed SQL AST/emitter.
Neither that API nor SQLGlot establishes a complete procedural compiler. The affirmative
SQL-standard body route must therefore be qualified separately from procedural lowering.
Do not weaken required DB checks or move them into caller-side preflight to meet a syntax goal.

The newly assessed SQLGlot addendum does expose procedural/DDL/DML/privilege representations;
representation is not equivalent to PostgreSQL generation. In exact v30.27.0, generic generation
of `IfBlock`, `WhileBlock`, `LoopBlock`, `RepeatBlock` and `Execute` reports unsupported syntax,
with no corresponding PostgreSQL overrides. See [generic generator](https://github.com/tobymao/sqlglot/blob/v30.27.0/sqlglot/generator.py#L6629-L6671)
and [PostgreSQL generator](https://github.com/tobymao/sqlglot/blob/v30.27.0/sqlglot/generators/postgres.py).
Strict generation must refuse those forms; an emitted warning or retained opaque command is not
a complete authoring product. Supported narrower nodes remain eligible for the comparison below.

## UM-06 — Structured native generation and admission

**Prerequisites:** UM-02 invariant observability/implementation contract; UM-05 working expression
products for a selected routine family; current native candidate/admission infrastructure. Early
body-kind/catalog design can begin from settled contracts. Activation needs the actual compatible
authoring, native deployment and admission implementation, not a declared capability flag.

First qualify one pure relational SQL helper or view and one companion projection body. Construct
its declaration/body from resolved metadata/expression nodes. Change inventory and catalog
observation together to support `prosqlbody`; bind native dependencies at the correct definition
time. Retain source attribution, error location and exact generated bytes. A string/native
predecessor and structured successor can coexist only through an explicit versioned comparison
and reader profile, never by silently treating their hashes as the same identity.

Then migrate appropriate pure SQL helpers and relational subexpressions, including scoped
selection/fact insert/delete predicates. Introduce only the small typed assertion/effect
realization justified by those actual routines. UM-02 defines whether failure codes are observable;
this package realizes that promise with correct SQLSTATE/outcome and failure timing.

Maintain in this package's investigation section a complete classification of maintained native
body families: pure SQL query/helper; set predicate plus assertion/mutation; trigger NEW/OLD/RETURN;
IF/RAISE; variable/record assignment; loops; dynamic EXECUTE; publication/lease/privilege sequencing.
For each, name the semantic owner, actual consumers, required constructs, selected lowering or
retained kernel, and the concrete gap/revisit trigger. This is part of the native design, not a
new standing capability register. No family receives a blanket PL/pgSQL exemption. Include catalog
inspection/admission queries in the migration inventory: use Inspector where its complete facts
satisfy the comparison, otherwise bounded typed Core catalog queries. Retire replaced catalog SQL
with its actual inventory/admission consumer; do not lose unrepresented properties to reduce text.

**UM-06-I1 — SQL-standard custody:** use an actual selected helper to settle parsing/printing,
`pg_get_functiondef`/catalog normalization, dependency binding, overload/result identity and
replacement behavior. Independently specify expected results, properties and refusals. An
unresolved equivalence blocks admission of that body profile, not unrelated Core work.

**UM-06-I2 — procedural coverage:** for selection/fact, then trigger and publication families,
compare finite typed relational/assertion/control-flow construction with retained specialized
kernels. Include suitable SQLGlot structured nodes alongside Core/pglast, with exact PostgreSQL
generation gaps distinguished from absent AST representation. Do not create a second native
catalog/authorization evaluator to exploit syntax coverage. Generated IF/RAISE must run at the required point; placing a mandatory guard in an
optimizer-reorderable expression is insufficient. If a construct cannot be preserved economically,
keep its explicit qualified kernel and report the remaining authorship obligation and reason.
Do not invent arbitrary procedural interpretation or claim complete SQL elimination.

**Acceptance:** actual runtime success and denial for the generated routine; NULL/duplicate/conflict
inputs; wrong release/overload/result; forged owner or search path; concurrent stale-attempt writer;
rollback before and after a guarded effect. For a changed declared invariant, prove its relevant
native implementation changes or admission refuses unsupported behavior. Comparing producer
metadata with its own rendering cannot establish correct enforcement.

## Alternatives, execution fit and completion boundary

A client-side Core/ORM rewrite would need equivalent independent-writer protection and privileges;
RC04 rejects replacing protected database enforcement. A universal procedural DSL would add
language/lowering/recovery obligations unsupported by the present need. Finite typed construction
functions and suitable SQL-standard bodies are the selected primary route, with named procedural
residue determined by UM-06-I2.

Keep set operations and source data server-local. Prepare immutable authoring/metadata products
once at their valid lifetime; invocation values do not regenerate native programs. Separate private
preparation from short publication fences while rechecking mutable premises atomically. Reduced
SQL maintenance is a design benefit; no speed, memory or capacity improvement is claimed.

UM-06/07 deliver a working generated/native/migration contract, not a source-printer demonstration.
Coordinate API/results with [typed operations](typed-domain-operations.md), comparison/invariant
meaning with [semantic contracts](semantic-contracts-and-policies.md), and relational inputs with
[UM-05](relational-implementations-and-projections.md). The coordinator owns integrated qualification.
Implementation, tests, probes, migrations and server qualification were **not_run** during plan creation;
the dated execution checkpoint below records subsequent work without claiming whole-series closure.
