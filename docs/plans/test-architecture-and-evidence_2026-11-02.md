## Target and foundation assessment

Separate native acquisition from application defaults, and observed context from requested settings.
One existing lifecycle owns each resource. Compose narrow test support around assurance needs,
keeping case-defining semantics and independent expectations visible. Reuse acquired bytes and
immutable preparation under complete dependencies; preserve fresh committed effects and deliberate
cold compilation/deployment. Diagnose actual native behavior through actual principals and clients.

FP-01/03/06 motivate coherent scenario owners rather than imports from test hosts. FP-02/04/05
require consumed behavior, owned semantics, independent expected results and reachable rejection
boundaries. FP-07/A4 motivates schema/scenario preparation reuse and bounded lifecycle machinery,
without treating real integration or independent checks as waste. A larger dataset, concurrent test
sessions, a model-field addition, a reordered catalog and interrupted authentication setup are the
change/growth scenarios. No speedup, capacity or blanket test-count benefit is claimed.

The current sealed native head, authenticated OID/name ownership and policy replay are useful
foundations. Do not replace them merely to adopt a plugin. The native companion compares complete
system/library arrangements before any wider fixture migration. Python and SQL test layers should
use established assertion/running capabilities without creating a universal test DSL, duplicate
validator, second catalog or parallel result ledger.
