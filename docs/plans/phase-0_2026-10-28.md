## 1. Purpose, scope and basis

**Outcome.** Phase 0 is the walking skeleton (D0 "Phases", row 0): the meta-model in PostgreSQL,
HTML ingest, the agent intervention tools, the typed query API and the evaluation harness, with
Opus extracting the claims of the first-pass dev pages through recorded tools. The full loop
(ingest, store, consolidate, serve, evaluate) works before any cheap method exists; later phases
hand stages to cheaper methods one at a time, each only when golden-set evaluation shows it
matches or beats what it replaces (D0, P12 in the [design rationale](../design/rationale.md)).

**Completion boundary** (the phase 0 gate, [D7 §9](../design/D7-evaluation-goldens-outer-loop.md#9-phase-gates)):

- the trace acceptance test passes on fixture proposals, deterministically (§3, decision 8);
- the live trace and spike-pages runs answer their typed questions from the database and score
  against the re-authored dev goldens;
- `ci eval` produces scores for dev, with intervals;
- the first `first-pass` run over the dev pages completes and is promoted (D7 §7 bootstrap).

**Not in phase 0:** encoders and readers (M04–M08, M12, M22), the local LLM tier (M10, M16), SymPy
conversion, slots, adjudication, linking beyond normalized labels, confidence models, derived
claims, exports, `kb.embedding`, GLiNER2 compilation (D4 §3 phase column; D5 §11 row 0).

**Basis.** D0–D9 and the [trace](../design/trace.md) as amended on 2026-10-28; ADR-0009…0018 (the
§B decisions in [DESIGN §2](../design/DESIGN.md)); the S0, S1 and S0-R2 evidence; the four library
research notes (`docs/design_review/evidence/2026-10-28_library-*`); the
[design-authority response](../design_review/evidence/2026-10-28_design-spikes/design-authority-response-S0-S1.md)
to the design owner's review.

**What the target must accommodate** (the change scenarios for the review, from
[DESIGN §1.3](../design/DESIGN.md)): a second domain pack beside statistics with no change to the
core; a table segment with quantities and units; a claim with `valid_time` and attribution; an
email thread's segment kinds; a rule with `or`/`not` conditions. Phase 0 implements none of these,
but nothing in `core`, `schema`, `consolidate`, `orchestrate`, `evaluate` or `serve` may assume
statistics.

## 3. Shared decisions

These are taken by the design authority (2026-10-28) before any supporting document is drafted,
because each binds more than one of them. Each states where the design records it.

1. **Each shape has one owner.** Hand-written Pydantic models in `core` own the domain-independent
   D1 shapes (values on `t`, condition nodes on `op`, bindings, batch items); `core.yaml` mirrors them
   under a contract test; the LinkML pack owns the domain vocabulary; the batch JSON Schema and
   `core/schemas/*.json` are generated from Pydantic models built per predicate from `SchemaView`
   (D2 §6, §7.3; D3 §6; ADR-0017). This replaces the earlier intent that LinkML be the one source:
   LinkML 1.12.1's Pydantic generator rejects the binding shape every batch uses and emits no
   discriminated unions ([schema-rules note](../design_review/evidence/2026-10-28_library-schema-rules/README.md) L-01, L-02).
2. **Batch ownership.** D2 §7.3 owns the envelope of the `ClaimProposalBatch`; `schema` compiles its
   per-predicate branches from the pack; `methods.llm.parse` (agent interface) owns the conversion
   from the model-facing form to the stored form, through the quote cascade (D4 §4.3). No other
   module defines batch shapes.
3. **The M19 context at both call sites.** One compiled rule serves submission and finalize through
   one claim view: `claim.id` is the local ref at submission and the key at finalize, `claim.key` is
   null at submission, each rule declares `at:`, and pool facts are cached view attributes from one
   view builder (D5 §8.2, D2 §7.4). Schema and rules owns the view builder and the runner; agent
   interface calls it at submission, consolidation at finalize.
4. **The queue and leases** are owned by orchestration (D6 §3): tasks, leases, expiry, retries and
   the agent barrier. The MCP queue tools and the golden tools consume them; golden passes are tasks
   with their own method (`golden.pass`), so `golden_next` leases through the same mechanism and no
   separate lease storage exists (D3 §8). **OPEN-D8-1 is decided: two processes** (D6 §1). `ci run`
   owns the orchestrator; the MCP server only reads and writes tables and sends `NOTIFY` in its
   submission transaction; the orchestrator listens with a timeout and re-queries. Golden passes are
   served by a golden-only server per subagent, whose instance id is the session reference (D8 §2.2).
5. **Packets.** Ingest and math owns a function that returns a unit's standing-context sentences,
   built from M13 binding sites (D4 §4.1). Agent interface owns packet assembly for extraction and
   golden passes, caps and splitting.
6. **Fixtures** are owned by foundations: `fixtures/trace` and `fixtures/s0` hold model-facing
   batches plus locators (D9 §1). The stored form is re-derived by the production quote cascade;
   tests compare by locator and structure, never by literal keys, because keys change with the
   rendition (D1 §10.1). Re-deriving the S0/S0-R2 batches on the production renditions doubles as an
   identity check against the spike offsets.
7. **Goldens are re-authored**, not imported (D7 §3.1): Sonnet passes A and B and a Sonnet
   adjudication session per dev unit, through the golden tools (ADR-0011). The v1 reference is the
   fixture proposals and a witness (D7 §6).
8. **Deterministic acceptance.** `tests/acceptance/test_trace.py` runs a `trace` slice with
   `agent_mode: complete`, submits the `fixtures/s0` batches for the trace units through the MCP
   tools in process (one shared FastMCP `Client(mcp)`), reruns the slice so the agent results are
   reused (D6 §4), then asks D8 §5.3's questions of that run (D9 §4). The live Opus trace run is qualification
   evidence, scored by alignment.
9. **Phase 0 scope.**
   - Schema v0 (with S4's corrections) and guideline v1 are frozen for phase 0 (D7 §9).
   - The first-pass run proposes for the dev pages; other non-test units are `skipped(budget)`; the
     agent works the queue across sessions (D6 §7.4).
   - `kb.embedding` and GLiNER2 compilation move to phase 1 (D3, D2 §7.2).
10. **Conventions.**
    - Package ids `P0-<doc>-<n>`, where `<doc>` is `F`, `S`, `I`, `O`, `A`, `C` or `E` (the seven
      documents in table order).
    - `ci` command groups belong to the document that owns their behaviour (`ci db` foundations,
      `ci schema` schema and rules, `ci ingest` ingest and math, `ci project`/`ci run`/`ci status`/
      `ci tasks` orchestration, `ci query`/`ci explain` consolidation and queries, `ci golden`/`ci eval`/
      `ci digest`/`ci promote`/`ci experiment` evaluation and goldens, `ci direct`/`ci ack`/`ci veto`
      agent interface); the Typer app and its registration belong to foundations.
    - Shared pytest fixtures (the per-session test database `ci_test_<pid>`, the trace slice, a
      compiled schema) live in `python/corpus-structure/tests/conftest.py`, owned by foundations.
    - Orchestration loads `methods.yaml` into the method registry; methods register their
      configuration models with it.
11. **APPARATUS-01 (provisional).** Product `evaluate/` implements D7 §5's alignment and scoring,
    ported from the instruments. The spikes keep their frozen I-R2 revision. Where the shared
    evidence apparatus lives long-term waits on the operator's design of the evidence system.
12. **Single home after a port.** Once a spike module is ported, the product module is its home;
    the spike series scores against its frozen revision (spike plan §3.5). The grammar is ported
    after S5-A has extended it.
13. **The TeX tokenizer and the token form live in `core`.** Keys need the token form (ADR-0012)
    and `core` depends on nothing, so the TeX-rules `regex` tokenizer, the sizing-command drop list
    and the token form are `core/tex.py`, owned by foundations; the grammar's normalizer and M01's
    macro reader consume the same tokenizer and drop list (D4 M01, M11;
    [text-math note](../design_review/evidence/2026-10-28_library-text-math/README.md) L-04, L-07).

Each supporting document carries the mechanisms it builds into its packages and cites the owner.

| Document | Mechanisms (design owner) |
|---|---|
| Foundations | Frozen, discriminated Pydantic models with a named recursive `Condition` and `Field(exclude_if=…)` defaults (D2 §6, D3 §6); keys from canonical JSON in Python, never from `jsonb::text` (D1 §10.1, D3 §6); the TeX tokenizer and token form (§3 decision 13); SQLAlchemy Core metadata (identity columns, a naming convention, named CHECKs from the same value lists as the types) with 0001 generated once and frozen (D3 §1); a psycopg-pool per process lent to SQLAlchemy; binary COPY with `Copy.set_types`; `on_conflict_do_update(…).returning()` for get-or-create (D3 §1, D6 §3); template-cloned test databases and the catalog comparison test; Hypothesis properties, with `st.from_regex` where a model uses `Field(pattern=…)` (D9 §4); the stateful lifecycle test belongs to orchestration and the grammar-generated math tests to ingest and math (D9 §4) |
| Schema and rules | `SchemaView` applicability through `class_ancestors` and `induced_slot`, native slots, the canonical-JSON schema hash, `linkml-lint` per file (D2 §2, §3, §7.1); batch models by `create_model` per predicate and one `TypeAdapter` per form with a custom `GenerateJsonSchema`, and the decoding-form rules (D2 §7.3); typed rule-engine contexts, `at:`, `tables:`, rejected builtins and the view builder (D2 §7.4, D5 §8.2); jsonschema as an independent test oracle, with `hypothesis-jsonschema` drawing batches from the exported schema (D9 §2, §4) |
| Ingest and math | html5lib through `lxml.html.html5parser` with `namespaceHTMLElements=False`, bytes in and recorded diagnostics; the cssselect2 `Matcher` as role engine; the named-list delimiter pattern with a timeout; the macro reader on the TeX tokenizer; the spaCy Doc built from words and spaces and `nlp.pipe`; Lark `edit_terminals`, `ordered_sets` and per-process parsers; spaCy `Matcher`/`PhraseMatcher` for M13 (D1 §3, D4 M01–M03, M09, M11, M13) |
| Orchestration | One claiming `UPDATE … FROM (SELECT … FOR UPDATE SKIP LOCKED)` that takes expired leases; `attempt` fencing; partial queue indexes; reuse resolved at task creation; `LISTEN`/`NOTIFY` as hints with timeout and re-query; rule-engine `Chain` for policies (D3 §8, D6 §1, §3, §7.1) |
| Agent interface | FastMCP lifespan pool, synchronous tools, Pydantic outputs and `ToolResult` packets; the loose batch parameter validated per item; the schema through `read_instructions`; caps in characters with page tokens; the golden server per subagent (D8 §1–§3); the served tokenizer's `encode_batch_fast` for LLM-tier packet caps (D4 §4.1); the quote cascade's token-sequence step (D4 §4.3) |
| Consolidation and queries | SQLAlchemy JSONB comparators; spans by `unnest` with `ON CONFLICT DO NOTHING`; `insertmanyvalues` where ids come back; ids pre-allocated with `nextval` so parent and child rows copy in one pass (store note §2–§3); built-in full-text search for `find` (D3 §5); Typer groups and `--json` result models (D8 §4) |

## 9. Review point

The binding requires a design/target review before a substantial stage. By operator decision
(2026-10-28) it runs with combined holistic and library-targeted focus on this coordinator, the
shared decisions and ADR-0013…0018 (the contract layer), before the supporting documents are
drafted, by a fresh `design-reviewer`. ADR-0007's audit-refresh prerequisite does not apply: no
production code exists to audit. Findings are dispositioned in §11 and folded in before drafting
continues. The proposed ADRs (0016–0018) are accepted after their spike evidence and this review.

## 10. Completion and qualification

Phase 0 is complete when:

1. every package of the seven documents is done by its own acceptance, with the command and date of
   each result;
2. `just test-all` and `just hygiene` pass on the same tree;
3. the acceptance test passes and the phase 0 gate (§1) is met, with the live runs' evidence
   recorded;
4. the first-pass dev run is promoted with `ci promote` (an operator act);
5. a design/target review of the assembled phase 0 (binding cadence, integrated stage boundary) has
   run and its findings are dispositioned.

The run order for qualification is: the `trace` slice (fixtures, then live Opus), then `spike-pages`,
then `first-pass` over the dev pages, with Sonnet golden passes for the dev golden set (D7 §3.1) in
parallel once the golden tools exist.

## 13. Standing conventions

- Code goes in `python/corpus-structure/` (D9 §1), domain data in `domains/`, fixtures in
  `fixtures/`; the spike folder is never imported.
- During a package, compile checks and focused tests; `just test-all` and `just hygiene` at the
  phase end (AGENTS.md); `just turn-end` at the end of a turn that changed files.
- Dependencies are pinned exactly and added only when a package uses them (D9 §2).
- Commits are small, name the package id, and state the test outcome. Nothing is pushed unless asked.
