## 1. Purpose, scope and basis

**Outcome.** Phase 0 is the walking skeleton (D0 "Phases", row 0): the meta-model in PostgreSQL,
HTML ingest, the agent intervention tools, the typed query API and the evaluation harness, with
Opus extracting the claims of the `phase0-golden` scope through recorded tools: the four spike pages
whole (LocationScale, Normal, LogNormal and Gamma: 208 units, which also hold the trace and core units; Weibull holds the worked examples and stays reserved) plus each dev golden unit by its unit
locator, about 234 packets. The full first pass is a phase 1 run with the local LLM (P0CL-09; the
operator chose the unit-level scope on 2026-10-28, after the evaluation document's simulation showed
that whole golden pages would be about 1,655 packets; [evidence](../design_review/evidence/2026-10-28_phase0-golden-size/README.md)). The full loop
(ingest, store, consolidate, serve, evaluate) works before any cheap method exists; later phases
hand stages to cheaper methods one at a time, each only when golden-set evaluation shows it
matches or beats what it replaces (D0, P12 in the [design rationale](../design/rationale.md)).

**Completion boundary** (the phase 0 gate, [D7 §9](../design/D7-evaluation-goldens-outer-loop.md#9-phase-gates)):

- the trace acceptance test passes on fixture proposals, deterministically (§3, decision 8);
- the live trace and spike-pages runs answer their typed questions from the database and score
  against the re-authored dev goldens;
- `ci eval` produces scores for dev, with intervals;
- successive `agent_mode: complete` runs over the `phase0-golden` slice converge with no unresolved
  agent tasks, and the operator promotes one after reading the pre-registered readings (D7 §7, §9).

**Not in phase 0:** encoders and readers (M04–M08, M12, M22), the local LLM tier (M10, M16), SymPy
values stored on claims (evaluation's value equivalence does use SymPy, D7 §5.3), slots, adjudication, linking beyond normalized labels, confidence models, derived
claims, `kb.embedding` (the embedding specification is declared in the model now; the table is
phase 1), GLiNER2 compilation (D4 §3 phase column; D5 §11 row 0). Since the second revision, a
Parquet run export, the relational pool with an in-process DuckDB engine, and typed
`ExternalReference` resolution (OPEN-D1-5, decided by RC11 of the alignment review) are in phase 0.

**Basis.** D0–D9 and the [trace](../design/trace.md) as amended on 2026-10-28; ADR-0009…0018 (the
§B decisions in [DESIGN §2](../design/DESIGN.md)); the S0, S1 and S0-R2 evidence; the four library
research notes (`docs/design_review/evidence/2026-10-28_library-*`); the
[design-authority response](../design_review/evidence/2026-10-28_design-spikes/design-authority-response-S0-S1.md)
to the design owner's review; the [design-principle audit](../design_review/audit/README.md) (source `024bb33`) and the
[domain-model alignment review](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md) with its [target model](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md), whose rule changes the operator decided
on 2026-10-28 (§9.2).

**What the target must accommodate** (the change scenarios for the review, from
[DESIGN §1.3](../design/DESIGN.md)): a second domain pack beside statistics with no change to the
core; a table segment with quantities and units; a claim with `valid_time` and attribution; an
email thread's segment kinds; a rule with `or`/`not` conditions. Phase 0 implements none of these,
but nothing in `core`, `schema`, `consolidate`, `orchestrate`, `evaluate` or `serve` may assume
statistics.

## 3. Shared decisions

These are taken by the design authority (2026-10-28) before any supporting document is drafted,
because each binds more than one of them. Each states where the design records it.

1. **One model; every representation is a governed projection** (alignment review RC01, RC03, RC04;
   ADR-0020 at P0-D-1, superseding ADR-0017; [R01](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r01), [target model §1–§5](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). This
   replaces the first revision's split, in which hand-written Pydantic models owned the core shapes
   and `core.yaml` mirrored them.
   - The **corpus-structure model** is LinkML in three modules: `core` (values, condition nodes,
     bindings, items per form, evidence, segment kinds, qualifier specifications, closed sets with
     member properties, the key-scheme declaration, `ExternalReference`), `system` (the classes of
     `meta`, `ops`, `kb` and `eval` with their closed sets, invariants, relationships and payload
     classes, the source-profile class and the `EmbeddingSpec`), and the domain packs.
   - `core` and `system` live in `python/corpus-structure/src/corpus_structure/model/` and change with
     code releases: together they are the **model revision** (LinkML `version`, the hash of their
     parsed canonical JSON, compiler versions, key-scheme version), logged in a checked-in revision
     file whose projection is `meta.model_revision`. Packs stay in `domains/` and are data: each is a
     **schema version**, whose D2 §2 hash now covers the model revision id instead of a mirror.
   - **Stage A** (now): the vocabularies with member properties, qualifier specifications, defaults,
     name tables and templated invariant validators are generated into the checked-in `core/_model/`;
     `core/vocab.py` is generated at its existing path. **Stage B** (after probe Q-1): the shape
     structure is generated too, or, if Q-1 fails, `core.yaml`'s shape classes are emitted from the
     Pydantic `model_fields` by an own emitter; either way no hand-kept mirror remains. Until Stage B,
     the mirror contract test is extended to every shape fact Stage A does not generate.
   - Generated files are never edited; each has a drift test. `core` keeps its runtime dependencies
     (Pydantic and `regex`); LinkML is needed only by `schema` and the generators. Behaviour stays in
     ordinary domain functions over the generated types; per-predicate batch branches stay `create_model`
     from `SchemaView` in `schema`.
2. **Batch ownership; authored batches are the authority.** D2 §7.3 owns the envelope of the
   `ClaimProposalBatch`; `schema` compiles its per-predicate branches from the pack. What an author
   writes (a golden pass, a fixture, an agent proposal) is stored as the model-facing batch plus its
   **citation frame** (each `sN`/`cN` mapped to the cited sentence's locator and text); the stored form
   is derived per rendition by `methods.llm.parse`, the quote cascade (D4 §4.3), an early agent-interface
   package (P0CL-03, P0CL-08; ADR-0019). Batch shapes are declared in the model (decision 1); no module
   defines them by hand once Stage B lands. A re-location writes a new citation-frame version with a
   parent link; frames are never rewritten in place (alignment review R06).
3. **The M19 context at both call sites.** One compiled rule serves submission and finalize through
   one claim view over the `core` keyed candidate set (claims, entities and statements, each with an
   `id` and a nullable `key`; since the second revision a complete translation of the batch with typed
   references and `MISSING` states, decision 21), which batches and the candidate pool both adapt into: `claim.id` is the local ref at submission and the key at finalize, `claim.key` is null
   at submission, each rule declares `at:`, and pool facts are view attributes declared by the pack's
   `views:` section (D5 §8.2, D2 §7.4). The view builder and runner are in `validate`, below
   `consolidate` (D9 §1), owned by schema and rules. At submission they run inside `propose_claims`,
   reading symbols with `core/tex.py` (grammar-dependent rules are `at: [finalize]`, so no grammar
   parse runs in an MCP worker thread); at finalize they run as one run-level step inside the
   consolidation pass (P0CL-08, -13, -14).
4. **The queue and leases** are owned by orchestration (D6 §3): tasks, leases, expiry, retries and
   the agent barrier. The MCP queue tools and the golden tools consume them; golden passes are tasks
   with their own method (`golden.pass`), so `golden_next` leases through the same mechanism and no
   separate lease storage exists (D3 §8). **Two processes** (D6 §1; OPEN-D8-1). `ci run`
   owns the orchestrator; the MCP server only reads and writes tables and sends `NOTIFY` in its
   submission transaction; the orchestrator listens with a timeout and re-queries. Golden passes are
   served by a golden-only server per subagent, whose instance id is the session reference (D8 §2.2);
   `write_golden` creates a unit's pass-C task in the transaction that stores the second of its
   passes A and B. Long runs are sequences of `agent_mode: complete` runs that reuse finished tasks;
   `wait` is for short slice runs (P0CL-12).
5. **Packets.** Agent interface owns M24's method definition (`select`, `input_digest`) and packet
   assembly, as a pure function of recorded inputs: the unit and its standing context (a function
   owned by ingest and math, from M13 binding sites) and the known entities of the run's recorded
   reference run only, or at bootstrap a page-level list from author markup (D4 §4.1). Caps are M24
   configuration in characters, one authority; the MCP tools only paginate what the assembler
   produced; the task records the served packet's hash (P0CL-05).
6. **Fixtures** are owned by foundations: `fixtures/trace` and `fixtures/s0` hold authored batches
   with their citation frames (decision 2). The stored form is derived by the production cascade on
   the production renditions; tests compare by locator and structure. Re-deriving the S0/S0-R2
   batches doubles as an identity check against the spike offsets. Fixture acceptance therefore needs
   I1, I2 and A0 (§7).
7. **Goldens are re-authored**, not imported (D7 §3.1): Sonnet passes A and B and a Sonnet
   adjudication session per dev unit, through the golden tools (ADR-0011). A golden unit is keyed by
   its locator-based unit key, its items are derived per rendition, and a citation frame that no
   longer resolves marks the unit stale (D7 §3.1, §3.5). The v1 reference is the fixture proposals
   and a witness (D7 §6).
8. **Deterministic acceptance.** `tests/acceptance/test_trace.py` runs a `trace` slice with
   `agent_mode: complete`, submits the `fixtures/s0` batches for the trace units through the MCP
   tools in process (one shared FastMCP `Client(mcp)`), reruns the slice so the agent results are
   reused (D6 §4), then asks D8 §5.3's questions of that run (D9 §4). The live Opus trace run is qualification
   evidence, scored by alignment.
9. **Phase 0 scope** (P0CL-09, -16; operator, 2026-10-28).
   - Schema v0 (with S4's corrections) and guideline v1 are frozen for phase 0 (D7 §9).
   - The phase 0 first pass is the `phase0-golden` scope (§1): the spike pages whole plus the dev
     golden units by locator, declared with a `{golden_set: <label>}` include resolved at run start
     and recorded on the run; other eligible units get `skipped` tasks with reason `scope`, so every
     unit's fate is recorded (D6 §7.4, §8). The full first pass is a phase 1 run with M10.
   - Test units route like any unit; test pages are excluded from every training, fitting,
     prompt-optimization and example set (D7 §4). The phase 0 slice holds no test page.
   - `kb.embedding` and GLiNER2 compilation move to phase 1 (D3, D2 §7.2); the `EmbeddingSpec` is
     declared in `system` now.
   - The alignment review's foundations are built in phase 0 (operator, 2026-10-28): the model and its
     projections, the relational projection, the change model, declared identity, the relational pool
     with its DuckDB engine, typed `ExternalReference` resolution and a Parquet run export.
10. **Conventions.**
    - Package ids `P0-<doc>-<n>`, where `<doc>` is `F`, `M`, `S`, `I`, `O`, `A`, `C`, `P` or `E` (the
      nine documents in table order); `D` marks the coordinator's design-authority packages (§9.2).
      Probes are `P0-<doc>-Qn`, keeping the alignment review's numbers (Q-1…Q-7); their evidence goes in
      `docs/design_review/evidence/2026-10-28_phase0-model-probes/` with record ids `p0q.*`, owned by
      this series.
    - Model tooling is `just model` (generate, check), owned by model and projections; `ci export`
      belongs to pool and interchange.
    - `ci` command groups belong to the document that owns their behaviour (`ci db` foundations,
      `ci schema` schema and rules, `ci ingest` ingest and math, `ci project`/`ci run`/`ci status`/
      `ci tasks` orchestration, `ci query`/`ci explain` consolidation and queries, `ci golden`/`ci eval`/
      `ci digest`/`ci promote`/`ci experiment` evaluation and goldens, `ci direct`/`ci ack`/`ci veto`
      agent interface); the Typer app and its registration belong to foundations. The pre-registered
      promotion readings shown by `ci promote` belong to evaluation and goldens (D7 §7).
    - Shared pytest fixtures (the per-session test database `ci_test_<pid>`, the trace slice, a
      compiled schema) live in `python/corpus-structure/tests/conftest.py`, owned by foundations;
      other documents add thin fixtures over their own public functions.
    - `ci mcp serve` belongs to agent interface.
    - Orchestration loads `methods.yaml` into the method registry; methods register their
      configuration models with it.
11. **APPARATUS-01 (provisional).** Product `evaluate/` implements D7 §5's alignment and scoring,
    ported from the instruments. The spikes keep their frozen I-R2 revision. Where the shared
    evidence apparatus lives long-term waits on the operator's design of the evidence system.
12. **Single home after a port.** Once a spike module is ported, the product module is its home;
    the spike series scores against its frozen revision (spike plan §3.5). The grammar is ported
    after S5-A has extended it.
13. **The TeX tokenizer and the token form live in `core`.** Keys need the token form (ADR-0012)
    and `core` depends on nothing, so the TeX-rules `regex` tokenizer, the sizing-command drop list
    and the token form are `core/tex.py`, owned by foundations; the grammar's normalizer and M01's
    macro reader consume the same tokenizer and drop list (D4 M01, M11;
    [text-math note](../design_review/evidence/2026-10-28_library-text-math/README.md) L-04, L-07).
14. **Identity follows content** (ADR-0019; P0CL-01, -04, -06). A rendition is keyed by its content
    (canonical text, segment tree, sentences); adapter configurations are build provenance
    (`kb.rendition_build`), so a content-preserving ingest change keeps every row and key. Statement
    and local-entity keys are anchored by locators; segment keys stay physical. `valid_time` and the
    cited source are identity qualifiers; numbers have a typed canonical decimal form. The locator
    contract (D1 §3.4) is one core-level function over segments, owned by ingest and math (package I0),
    which foundations' keys, orchestration's slices, the fixtures, the queries and `ExternalReference`
    resolution all use (OPEN-D1-5, decided by the alignment review's RC11).
15. **Reuse by content** (P0CL-02). A task's digest covers the content it reads (unit text, upstream
    observation payload hashes, compiled-artifact and prompt-part hashes, model revision, and for M24
    the served packet's hash); task ids are provenance only (D4 §1, D6 §4). Orchestration owns the rule;
    each method owns its digest. Keys are produced under a declared **key scheme** recorded beside them
    (decision 20). Under the run option `agent_reuse: by_unit`, M24's digest covers only the guideline
    sections that apply to the unit, through a declared section → unit-feature mapping that
    over-approximates (a section that recorded features cannot exclude applies everywhere); the option
    is kept and defined, not removed (operator, 2026-10-28, deciding RC13 otherwise; DA-017).
16. **Recorded inputs and served coverage** (P0CL-05, -11). Every run records its reference run
    (`ops.run.reference_run_id`, immutable; consolidation, M14 and packets read only it), its model
    revision, schema version and key scheme. Its knowledge is cut by `ops.run.cut_at`, sealed in a short
    transaction; the final pass, measure and evaluate read as of the cut, and fates are
    `finished_at <= cut_at` (RC10; R08; DA-024). Every
    typed-query result carries the run id it was served from and coverage for its scope; `promoted` is
    resolved once per journey and page tokens bind the run and query version (D8 §5). Orchestration
    records the fates; consolidation and queries reports them.
17. **Domain semantics stay in the pack** (P0CL-07). Pack annotations (`ci:param_map`,
    `ci:parameter_class`), the `family_structure` subset and the `views:` section carry what was
    statistics-specific in core; statement synthesis from containment is declared in the source
    profile; source profiles live in `sources/<profile>.yaml`; statistics queries are the pack's
    plug-in (`domains/statistics/queries.py`) behind a `serve` protocol (D1 §6.1, D2 §3, §7.4, §12.1,
    D5 §3.5, §4, D8 §5.2, D9 §1). The acceptance check for this is a toy second pack that runs the
    generic stages with no core edit, in consolidation and queries. Since the second revision it also
    exercises pack-scoped statement kinds, a case-preserving identity slot (`ci:case preserve`),
    `ci:key_role` and a business modality member with `attribution_identifying` (the A3 closure).
18. **The relational projection and the physical overlay** (RC03, RC05, RC06; [R05](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r05);
    [target model §6](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). SQLAlchemy `MetaData` is generated from the model into the checked-in
    `core/db/_tables.py` and drives Alembic; D3's DDL is no longer the authority (D3 and D2 cite model
    files and generated renderings). Every relationship a query joins on or an invariant constrains is
    relational (edge tables `kb.claim_ref` and `kb.claim_entity_ref`, identity rows `kb.entity_identity`,
    `ExternalReference` rows); decision-relevant scalars (modality, polarity, attribution) are columns;
    other values stay typed JSONB under the payload-schema registry. Static closed sets are `text` with
    named CHECKs; schema-version-scoped sets are per-version member rows with composite FKs. Physical
    access-path choices (indexes, BM25 partial predicates, views, the extension assertion) live in one
    hand-written overlay, `core/db/overlay.py`, bound by name to generated tables and failing at import
    on a missing name; model and projections owns it. Migration 0001 is generated once from this and
    frozen. The same-run invariants INV-03 and INV-08 are enforced by FK or, if probe Q-4 chooses it, in
    foundations' bulk-write primitives (F4) with a test per invariant.
19. **Schema change is modelled** (RC09, RC12; ADR-0022; [R06](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r06); [target model §9](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). A
    change record holds its compatibility class, reason, authorizing circumstance and migration mapping;
    the class decides the route. The payload-schema registry (`meta.payload_schema`, with
    `payload_schema_id` on every row that crosses revisions) holds each payload class's JSON Schema id,
    Arrow schema bytes, `sql_visible` paths and upcasters; readers dispatch by recorded schema and refuse
    an unknown id. Alembic revisions are linked (`template_args`, `process_revision_directives` refusing
    an unregistered revision, `on_version_apply`). **The operator's no-migration route** applies only to
    immutable, versioned payloads that no constraint, key, index or query reads, and to their Parquet and
    DuckDB projections; a change that touches anything PostgreSQL enforces or reads takes a migration.
    Source profiles are typed against core vocabulary and validated against the run's schema version.
20. **Identity is declared** (RC07, RC08; ADR-0023, extending ADR-0019; [R02](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r02); [target model
    §8](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). Each qualifier's key role (identity, meaning-bearing or inert, with conditional roles as
    member properties such as `attribution_identifying` on `cited`) and its canonical form by declared
    range are compiled into `KeySchema`. Case policy (`ci:case`) preserves case for math-bearing labels
    and slots. The key scheme is recorded per run and per judgment target; a scheme change ships a
    carry-over map; conformance vectors pin values per scheme, while fixtures still compare equalities.
21. **Owned translations and one owner of reference checks** (RC11, RC19; [R04](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r04); [target model
    §7](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). The translations T1–T8 of target-model §7 (authored → stored, stored → keyed candidate,
    candidate → rule view, row ↔ Arrow, model ↔ decoding form and the rest) are complete contracts with
    model-derived completeness tests. References are typed by kind; an unresolved reference is a typed
    `ExternalReference` node, never a dropped claim. `validate` owns reference and type checks for
    batches; the keying resolver owns kind refusals for pool candidates.
22. **Engine placement and the relational pool** (RC02; ADR-0021, superseding ADR-0016; [R09](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r09),
    [R10](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r10); [target model §10](../design_review/reviews/design_review_domain-model-alignment_2026-10-28_target-model.md)). PostgreSQL is the transactional authority for instances;
    the model is the authority for structure and meaning. The consolidation pool is a set of model-typed
    Arrow relations loaded as of the cut. Its set-based steps run in an in-process DuckDB 2.0 engine with
    no persistent state, beside a Python reference implementation that must be set-equal. Identity,
    canonical forms, TeX, SymPy and inference stay in Python and reach the engine as data. Determinism
    rules: sets, explicit `ORDER BY` key, ordered aggregates.
23. **Typed operational vocabularies and reason codes** (RC14; [R07](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r07)). Stage names, skip
    reasons, task unit types, drop and frame-failure reasons, confidence sources, judgment decisions and
    policy chains are modelled vocabularies. Policy symbols are typed and their literals checked at
    compile; keying and frame outcomes carry codes, and messages are projections of them.
24. **Derivation conformance is not independent assurance** (RC16; [R12](../design_review/reviews/design_review_domain-model-alignment_2026-10-28.md#r12)). Agreement among
    projections generated from one model (Pydantic and jsonschema; generated JSON Schemas and models) is
    called derivation conformance. Each contract names its independent semantic controls: hand-authored
    known-answer vectors, negative store tests per invariant written from D1 §11, the external S0 and
    S0-R2 batches, relational key oracles and tex parity.
25. **Several packs form one schema version** (alignment review §1). A project that combines packs
    compiles them into one schema version, with local names checked for uniqueness at compile; the rule
    view's local qualifier names rely on it.
26. **Deployment settings stay outside the model** (focused pydantic-settings review, 2026-10-28; a
    refinement of the alignment review, no recommendation changed). `settings.py` stays hand-written
    `pydantic-settings` (2.16.1) with constructor and environment sources only; settings are
    result-neutral by contract, never stored, hashed or recorded as configuration (D2 §12.1, D9 §3).
    **No model-projected class is a `BaseSettings`**: validating one reads the environment
    (`model_validate({})` returned the environment value under 2.16.1; scratch check, to be recorded as
    `p0q.settings-env` by F5), so a stored `ops.run.options` or method `params` re-read through it would
    silently mix in the current environment (DP-24, DP-09). Method-configuration merging (`defaults ⊕
    named params`) stays an own pure function, never the library's layering, which goes through a private
    Pydantic helper. Settings import generated closed sets (`GpuMode`, `AgentMode` from M1). A setting may
    supply only a result-neutral default; the run records the resolved value (explicit option > setting >
    model default). `MethodContext` exposes a narrowed, typed view of result-neutral settings only.

## 13. Standing conventions

- Code goes in `python/corpus-structure/` (D9 §1), domain data in `domains/`, fixtures in
  `fixtures/`; the spike folder is never imported.
- During a package, compile checks and focused tests; `just test-all` and `just hygiene` at the
  phase end (AGENTS.md); `just turn-end` at the end of a turn that changed files.
- Dependencies are pinned exactly and added only when a package uses them (D9 §2).
- Commits are small, name the package id, and state the test outcome. Nothing is pushed unless asked.
