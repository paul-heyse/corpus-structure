# Comparative-review probes: Alembic drift at head, template-clone privileges and preparation cost

**Purpose.** These probes settle two decisive premises for the
[comparative library-leverage review](../../../library_leverage/reviews/README.md):
- **CBO-008:** whether Alembic's configured comparison is clean at head.
- **CBO-010:** whether a template clone keeps the database-level TEMP privileges that the revisions
  establish, and whether a generic replay restores them.
- **CBO-003** (no database): how much of cold release preparation is graph generation. See Q3.

## Environment

- Dedicated PostgreSQL 18 cluster `18/corpus` on port 5434, reached through the maintenance
  principal (`connection_settings(settings, "maintenance")`).
- Databases were created from `cs_template` and migrated with `semantic.migrations.upgrade`. This is
  the same route the native test fixture uses.
- Library versions:
  - SQLAlchemy 2.1.5
  - Alembic 1.20.0
  - psycopg 3.3.6
- Python 3.14.10.
- Source: HEAD `346bfe1` with the concurrent working tree. The migrated head was `semantic_0029`.
- Run on 2026-10-29.
- Two throwaway databases were used, `cs_sem_probe_<pid>_<hex>_t` and `cs_sem_probe_<pid>_<hex>_c`.
  Both were dropped in `finally` using the fixture's plain `DROP` with retry. The `residue` count
  read afterwards was `0`.
- Port 5432 and the operational database were not touched.

## Outcome (passed: all three questions answered)

### Q1, CBO-008: Alembic's configured check is not clean at head

`command.check(alembic_config(conn))` uses the repository's `env.py`, which already sets
`include_schemas`, `include_name`, `compare_server_default` and the CHECK-by-name plugin. It raised
`AutogenerateDiffsDetected` with **49 differences**: 24 `remove_constraint`/`add_constraint` pairs
and one `modify_default`.

**Naming divergence.** Most pairs are CHECK or UNIQUE constraints that the frozen SQL migrations
named by hand or left to PostgreSQL's default. Examples are `alternative_group_operation_id_check`,
`coverage_translation`, `entity_source_realization_id_…_key` and `uq_observation_bound`. The derived
MetaData names the same constraints `ck_<table>_physical_<digest>` or `uq_<table>_<columns>`. Tables
affected:
- `sem.conditional_atom`, `sem.conditional_rule`
- `data.alternative_group`, `data.coverage`, `data.assessment`, `data.entity_source`,
  `data.occurrence_context`, `data.publication_intent`
- `kb.observation`, `kb.observation_input`
- `ops.measurement`, `ops.method`, `ops.completed_result`, `ops.task`
- `eval.document_split`

**Digest divergence with equal expressions.** For `eval.document_split`, the database holds
`ck_document_split_physical_23de252598` and the MetaData expects `…_a319d8e82e`, yet the CHECK
expression is the same. The digest that was frozen into the revision no longer matches the current
derivation.

**Unique constraints that may differ in columns.** `kb.observation` has unique constraints named
`uq_observation_bound` and `uq_observation_source_identity`. The MetaData expects
`uq_observation_release_id_id` and `uq_observation_release_id_observation_key`. Whether their
columns differ, and not only their names, was not inspected.

**Server default.** `ops.task.invocation_key` differs between the database and the MetaData.

**Not compared.** As documented, Alembic does not compare functions, triggers, grants or views.

**Warning.** `env.py` emitted an SAWarning about unresolvable foreign-key cycles among `data.batch`,
`data.project`, `data.realization`, `ops.completed_result`, `ops.input_cut` and `ops.run`.

### Q2, CBO-010: a template clone loses database-level privileges, and a generic replay restores them

| Database | `datacl` | TEMP per role (publisher / writer / reader / evaluator) |
|---|---|---|
| Migrated template | `{=c/paul,paul=CTc/paul,corpus_sem_publisher=T/paul,corpus_sem_writer=T/paul}` | true / true / false / false |
| Clone (`CREATE DATABASE … TEMPLATE <template>`) | `NULL` (defaults, so PUBLIC has TEMP) | true / true / **true / true** |
| Clone after `aclexplode` replay (`REVOKE ALL … FROM PUBLIC`, then re-`GRANT` each template entry) | the same set as the template; only entry order differs | true / true / false / false |

Object-level privileges survived the clone unchanged. In both databases the reader could SELECT but
not INSERT on `data.entity`, and the writer could EXECUTE `data.begin_stage()`.

### Q3 (CBO-003): release preparation cost and its graph share (measured)

This was added for the G2 judgment. It needs no database. The probe is
[probe_prepare_timing.py](probe_prepare_timing.py), adapted from the reviewer's scratch timing. It
ran on 2026-10-29T15:32-04:00, at HEAD `0350a7a`, with Python 3.14.10 on one workstation. The
subject was the statistics pack, which has 100 classes. It used the composed `prepare_pack` inputs,
pickled to a scratch directory outside the repository.

Raw lines are in [prepare_timing.txt](prepare_timing.txt). Each figure is the range over three
fresh processes:

| Step | Seconds |
|---|---|
| `prepare_pack` (acquisition plus layering plus preparation) | 3.66 (one run) |
| Package import | 1.19–1.32 |
| Cold `prepare_release` (what `load_release` does in a new CLI process) | 2.18–2.45 |
| … of which `ontology.build_graph_artifacts` (OWL/SHACL) | 1.03–1.12 |
| … of which the execution companion compile | 0.68–0.78 |
| … of which `_view_and_vocabularies` | 0.23–0.27 |
| Second, uncached `_prepare_release_uncached` in the same process | 1.22–1.32 |
| … of which graph artifacts | 0.89–0.96 |

These numbers support only the claim that graph generation is roughly half of cold re-preparation
for this pack on this machine. They are not a whole-suite or capacity measurement.

## Limits

- The diff was not normalized beyond Alembic's own comparison.
- Whether any constraint pair differs semantically, apart from the observation unique constraints,
  was not examined.
- Clone timing was not measured.
- Only the database ACL was replayed; `ALTER DATABASE … SET` parameters were not examined.
- These are single runs on one cluster.
