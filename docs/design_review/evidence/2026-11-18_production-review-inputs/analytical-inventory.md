## 9. How data crosses from PostgreSQL to analysis

Three transports, all in `src/`:
1. SQLAlchemy 2.1 Core over psycopg 3.3 (psycopg-pool): the default. Pool in `core/db/store.py` (`ConnectionPool`, `NullPool` SQLAlchemy on `creator=pool.getconn`, `set_json_loads(json.loads)` :66, `PooledConnection` :55). Rows arrive as Python objects (`.mappings()`, `yield_per`), jsonb decoded by `json.loads`; results of native programs are typically one jsonb document per call (`DataOperationStorage.read_demand_result`, `data_operation_storage.py`). Used by every serving path except the two ADBC users.
2. ADBC (`adbc-driver-postgresql==1.13.0`): `core/db/adbc_lifetime.py:15-37` `open_adbc_connection` (explicit driver path or packaged driver; `type_resolver_mode` builtin/server). Users: (a) `serve/companion_export.py:137-200` (snapshot-importing second session, `use_copy=true` with `batch_size_hint_bytes` from settings, `fetch_record_batch()` -> Parquet); (b) `serve/database_description.py:235-263` (catalog introspection: `adbc_get_objects`, execute-schema/statistics, `use_copy=false`). No other `fetch_arrow`/`fetch_record_batch` use (grep).
3. Writes into PostgreSQL from Arrow: `semantic/arrow_transfer.py:134-171` `copy_arrow_stream` (psycopg `cursor.copy(... FORMAT BINARY)` on the existing Core connection's driver connection; `pgpq` encoder; schema check per batch). Users: `semantic/releases.py:391-405` (release archive), `semantic/pdf_staging.py:207`, `semantic/pdf_publication.py:438`.
- There is no DuckDB postgres scanner/attach, no Arrow result path from SQLAlchemy sessions, no `COPY ... TO`/psycopg read-side Arrow conversion. Python-built Arrow tables enter DuckDB via `from_arrow` (D1, D3, D4) or files via `from_parquet` (D2); Arrow produced from PostgreSQL leaves only through the companion ADBC path.
- Cancellation/lifetime around both drivers: `core/db/lifetime.py`, `core/db/cancellation.py` (`ADBCBorrowerCancellation`, `BorrowerCancellation`).
