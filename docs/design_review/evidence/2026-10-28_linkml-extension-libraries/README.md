# LinkML extension libraries: fit for the phase 0 model, 2026-10-28

**Status, 2026-10-28: done.** This is the evidence behind a focused review, run by a fresh
design-reviewer. The review asked whether the LinkML extension libraries change the phase 0 target
design. The operator's overview ([linkml extension libraries](../../../libraries/linkml_extension_libraries.md))
was used for feature discovery. The conclusion is that they refine the design without changing it:
no library is adopted in phase 0, and every bespoke piece the plan builds stays bespoke.

The plan consequences are recorded in:
- [coordinator §6](../../../plans/phase-0_2026-10-28.md), the "not used" list;
- [model and projections](../../../plans/phase-0/model-and-projections.md) §3.2, enum expansion, and §3.6,
  the change model.

## What was tested

The probes ran on Python 3.14.10 with linkml-runtime 1.12.1, in throwaway environments: linkml-map
0.5.4 and 0.6.0rc1 with pint 0.25.3, and oaklib 0.7.4. The environments are not kept. To rerun, install
those versions and run the scripts against `code/`.

- **linkml-map** (`code/run.py`, `code/run2.py`, with `v1.yaml`, `v2.yaml`, `spec.yaml`). The test maps a
  payload from v1 to v2 with a slot rename, an enum member rename, a nested class, absent and null fields,
  and a polymorphic `designates_type: t` list. Outputs are in `results/linkml-map-*.txt`.
  - **Polymorphic list.** Without a base-class derivation the transform fails ("Could not find class
    derivation for Value"). With one, the subclass fields are silently dropped: the output is
    `[{"t":"NumberValue"},{"t":"TextValue"}]`.
  - **Absent versus null.** Absent fields come out as `null`.
  - **Unknown enum values.** In 0.5.4 an unknown value becomes `null` even with `strict=True`.
  - **Inversion** works for renames.
  - **`derive-schema`** keeps the source enum members on an enum rename.
  - **Import.** `import linkml_map` needs pint below 0.26, because ucumvert's definitions fail pint 0.26's
    parser.
- **OAK `ValueSetExpander`** (`code/enumrun.py`, `code/enums.yaml`; output in
  `results/oak-enum-expansion.txt`). The test expands a `ClaimModality`-like enum, with `in_subset`
  member properties, through `inherits`, `include` and `minus`.
  - `SchemaView.induced_enum` returns only the enum's own members, and nothing for a composed enum.
  - OAK expands `inherits` correctly.
  - OAK duplicates the `include` member and ignores `minus`.
- **Package metadata and import checks** (`results/pypi-metadata/`).
  - **linkml-datalog 0.2.0** does not import on linkml-runtime 1.12.1, and needs an external Soufflé
    binary.
  - **schema-automator 0.5.7** has no schema diff. Its `import-sql` reads no CHECKs, nullability or
    composite keys.
  - **valuesets 0.4.2** has no static materializer for enum expressions.

A broad search found **no schema-diff tool** in linkml 1.12.1, linkml-runtime 1.12.1, linkml-map,
schema-automator, the LinkML GitHub organization or PyPI. An empty search does not prove absence;
ADR-0022's own diff stands.

## Decisions it supports

| Library | Decision | Trigger |
|---|---|---|
| linkml-map | adopt later, at compile time only, with a pint hold | a cross-model mapping: an export to an external standard, an import of external data, or phase 2 expression-level splits and merges; or upstream fixes for polymorphic dispatch and absent fields |
| schema-automator | adopt later | pack authoring from data dictionaries, or enum annotation through OAK |
| oaklib, linkml-term-validator | adopt later | `meaning` CURIEs on pack terms, or ontology-backed `ExternalReference` resolution |
| valuesets, linkml-datalog, linkml-project-copier, linkml-store, schemasheets | not applicable | — |
