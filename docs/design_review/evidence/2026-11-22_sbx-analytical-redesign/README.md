The probe uses six synthetic rows in two batches, one Arrow thread and one DuckDB query
thread. DuckDB's buffer-manager and temp-spill limits are 64 MB and 16 MB for the Python
connection. The CLI runs an eight-row in-memory plan inspection. The successful recording
observed peak child RSS of 173,944 KiB via GNU time. This is an observation of the probe
processes under that invocation and supplies no production capacity or speed estimate.

- Acero projects an inversion predicate and uses one grouped node for multiplicity and
  inversion totals. DuckDB runs the equivalent grouped computation from an Arrow reader.
  Both match independently written expected rows, including separate report roles at ordinal
  zero and one invalid annotation in a duplicate group.
- DuckDB 2.0.0 refuses the second consumption of a relation backed by the same Arrow reader.
  Materializing that input explicitly allows both consumers to obtain all six rows.
- CLI `EXPLAIN (FORMAT JSON)` exposes a hash group operation in a separate small control.

Exploratory runs under `prlimit --as` at 1, 2 and 8 GiB exited 139 during the combined
run. The stack trace at 8 GiB reached DuckDB connection initialization. The successful
run used the time, input, affinity, engine and file limits above without the address-space
limit. The address-space result does not establish a memory leak or its cause. PostgreSQL,
provider execution and product qualification were `not_run`.
