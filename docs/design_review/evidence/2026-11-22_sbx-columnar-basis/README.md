# A typed, set-shaped basis for Set-Based Execution: library and boundary probes

**Tested · 2026-11-22.** These probes inform the
[typed-basis review](../../../plan_improvement_reviews/set-based-execution-columnar-basis_2026-11-22.md).
Source baseline `b5ff78b22`. Linux x86-64, CPython 3.14.10, PyArrow 26.0.0, DuckDB 2.0.0 (Python
and CLI `d54cbbe3df`), adbc-driver-postgresql 1.13.0, pgpq 0.12.0, psycopg 3.3.6, PostgreSQL 18.7.

The probes settle library contracts that decide whether a typed relation can carry a population
from producer to authority and back. They use synthetic data. None takes a timing, and none
exercises production schemas, purpose-role permissions, claims or recovery.

| Folder | Question | Run |
|---|---|---|
| `identity/` | Is the present partition identity reproducible from typed columns in DuckDB and PostgreSQL? | `uv run --no-sync python docs/design_review/evidence/2026-11-22_sbx-columnar-basis/identity/identity_parity.py` |
| `pyarrow/` | Are IPC bytes canonical; does a fused Acero plan stream; what does schema-driven JSON reading enforce? | `uv run python <folder>/pyarrow/<probe>.py` |
| `duckdb/` | Can one plan validate, diagnose and digest with canonical bytes; what do JSON reading, readers and the `postgres` extension guarantee? | `uv run python <folder>/duckdb/<probe>.py`; `duckdb -no-init -f <folder>/duckdb/pg_readonly_probe.sql` |
| `boundary/` | Can typed rows be staged, processed by a set routine and returned typed in one transaction, and with what fidelity? | `uv run python <folder>/boundary/<probe>.py` |

**Results.**

- All 60 synthetic partitions (440 items) gave the same identity from Python `canonical_identity`,
  the installed recursive `data.ddo_identity`, a DuckDB aggregate over typed columns and a
  PostgreSQL aggregate over a typed relation. Absent fields needed explicit presence handling.
  Decimals, floats, timestamps, sets, bags, optional-value tags and nested mappings are not covered.
- Arrow IPC bytes differ for logically equal data built by different routes. They can seal a
  transfer; they cannot name content.
- An Acero plan ran lazily over a Python source. `to_reader` applied no backpressure when threaded,
  and joins and aggregates neither preserve order nor spill.
- One DuckDB statement validated a nested token stream against four invariants, reported typed
  diagnostics and produced per-block digests equal to the repository's canonical JSON digests
  (40 of 40). DuckDB JSON reading coerces and ignores unknown keys; `pyarrow.json` with an explicit
  schema rejects them.
- Staging by COPY, a set-returning routine with no document parameter and a typed result worked in
  one session and one transaction, on ADBC and on psycopg. ADBC cannot join a SQLAlchemy
  transaction. Most purpose roles lack TEMP. ADBC truncates nanosecond timestamps on ingest and
  wraps `infinity` on fetch without error.

The PostgreSQL legs used a worker-owned scratch database that was dropped, `pg_temp` in
`corpus_structure_dev` with rollback, and read-only catalog and attach queries. The development
database holds a prior root. DuckDB extension installs wrote only under `~/.duckdb/extensions/`.
