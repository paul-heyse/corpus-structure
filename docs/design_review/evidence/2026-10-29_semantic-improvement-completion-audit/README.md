# Overlapping lazy boundary identities

**Failed conformance control, 2026-10-29; source `d004504`.** Consumed by SP-I04 and
CA-13 in the semantic-model-pivot completion audit. This is supporting evidence, not a
separate audit report or authority.

Question: after opening archived products and validating `B -> C`, does requesting the
overlapping `A -> B -> C` closure preserve the model identities used by the same release?

```bash
uv run python docs/design_review/evidence/2026-10-29_semantic-improvement-completion-audit/lazy_boundary_identity.py
```

The isolated control uses actual preparation, archived-product reconstruction, model validation
and property adapters. It touches no database, provider or operational realization. Python
3.14.10 and Pydantic 2.14.1 were recorded on the Linux operator host.

The recorded result shows both class identities replaced. The property's plain dictionary is
accepted, but its previously validated same-release instance raises `model_type`. This confirms
an order-dependent public validation boundary; it establishes neither storage corruption nor an
admission bypass. Repair must preserve demand loading while maintaining canonical per-release
models/adapters across overlapping closures.

Sources: `lazy_boundary_identity.py`; original output and stderr under `raw/`.
The pinned [Pydantic model-type documentation](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/errors/validation_errors.md#model_type)
describes the expected model-instance boundary; the control establishes the release's actual
class replacement and resulting public validation disagreement.
