# S4 · LinkML compilation

**Brief, 2026-10-28; revised after S0, S1 and S0-R2.** CPU. Ready and independent of the other
spikes; its outputs help S2 and S3, which can otherwise hand-write their schemas.

## Question

Does the statistics schema v0 of [D2 §9](../../../design/D2-schema-and-guidelines.md#9-statistics-schema-v0),
written in LinkML 1.12.1 with the `ci:` annotations, load cleanly and compile into what each
consumer needs, as D2 §7 specifies: schema tables, GLiNER2 schema dicts, the ClaimProposalBatch
JSON Schema (model-facing and stored forms), rule-engine rules including the guideline warnings,
and the annotator reference that replaces the prompt inventory?

## Design questions it answers

| Id | Question |
|---|---|
| OPEN-D2-1 | Exact `Schema.from_dict` keys for structures, attributes and thresholds in gliner2 2.1.0 |
| OPEN-D2-3 | rule-engine syntax for `rules.yaml` checks; custom functions or resolver-backed symbols |
| OPEN-D2-6 | Whether list-valued annotations round-trip through `SchemaView` |
| D2 §7.3 | Whether the per-predicate `oneOf` batch schema, with `cN` citations, `alternatives` and `extent`, validates the v1 batches and is accepted by vLLM's structured-output backend |
| D2 §7.4 | Whether the guideline rules S0-R2 checked in Python compile as rule-engine `guideline:` warnings |
| D2 §7.5, §10.10 | Whether the annotator reference can be generated from `SchemaView` with the information S0-R2's reference carries (A2) |
| D2 §2 | Whether the schema version hash is stable across loads and machines |

## Inputs

- The schema spike copies `code/schema/core.yaml` and `code/schema/statistics.yaml`, which equal
  D2 §6 and §9. Start from them; `rules.yaml` does not exist yet.
- D2 §3–§5 and §7 (vocabulary, predicates and qualifiers, compilers, including §7.4's
  `guideline:` group) and the initial `rules.yaml` in §9.
- S0-R2's annotator reference, `results/s0r2/inputs/packet_v1/reference.md`, generated by
  `code/s0r2_inputs.py`, and its worked examples (`results/s0r2/examples/`).
- S0-R2's guideline-rule checks, `code/s0r2_rules.py` (run by `code/s0_check.py --rules`).
- The model-facing format S0-R2 used, `results/s0r2/inputs/packet_v1/format.md`.
- Batches to validate: the v1 reference in model-facing form (`results/s0r2/reference_model_v1/`)
  and stored form (`results/s0r2/reference_v1/`), the three worked examples, and the S0 stored
  batches (`results/s0/stored/`, `results/s0/reference/`).
- **Renditions.** M01 produces renditions with html5lib (D4 M01); S0 and S1 used libxml2. On the
  seven pages S0 and S0-R2 use, the two are content-identical: same text, segments, sentences and
  offsets; only keys differ, because the rendition key hashes the parser (record
  [s1.rendition-identity](records/s1.rendition-identity.json)). Take renditions, sentence ids and
  offsets from `sample.json` and `results/s0r2/sample.json`, the libxml2 renditions the references
  are stored on.
- Library overviews: [linkml](../../../libraries/linkml.md), [gliner2](../../../libraries/gliner2.md),
  [rule-engine](../../../libraries/rule-engine.md).

## Procedure

1. **Schema files.** Copy `code/schema/*.yaml` to `results/s4/schema/` and write `rules.yaml`
   from D2 §9's initial rules and §7.4. Record every place where D2 is ambiguous or where LinkML rejects a
   construct, and how you resolved it.
2. **Load and lint.** `linkml-lint`; `SchemaView` with imports; induced slots for every class;
   read back every `ci:` annotation, including lists (`OPEN-D2-6`).
3. **Compile to schema tables** (D2 §7.1): rows for `meta.schema_class`, `schema_slot`,
   `schema_enum`, `schema_rule` as JSON. Compute the content hash twice in separate processes.
4. **Compile to GLiNER2** (D2 §7.2): the `Schema.from_dict` dict and the `JointIE` schema. Load
   both with gliner2 2.1.0 and run one trivial extraction on a trace sentence to prove they are
   accepted. Record the accepted keys (`OPEN-D2-1`).
5. **Compile to JSON Schema** (D2 §7.3): the stored form and the model-facing form (quotes).
   Extend both beyond D2 §7.3's current text to what the v1 batches use: `cN` citations of
   standing-context sentences outside the unit, `alternatives`, and `extent` on local entities;
   record each extension as proposed schema text. Validate with `jsonschema` (draft 2020-12) the
   v1 reference in both forms, the worked examples and the S0 batches, and run the entity-type
   side-table check in a few lines of Python. If the vLLM environment is available, check that
   the model-facing schema compiles in its structured-output backend (offline, without a model,
   if the backend allows; otherwise note it for S3).
6. **Compile rules** (D2 §7.4): each rule's `when` and `check` with `rule_engine.Rule` under a
   typed `Context`; register `family_params` both as a custom function and as a resolver-backed
   attribute; evaluate on the v1 reference claims, including one deliberately wrong claim per
   rule. Report which form type-checks cleanly (`OPEN-D2-3`).
7. **Guideline warnings** (D2 §7.4, A2). Express each check in `code/s0r2_rules.py` as a rule in
   a `guideline:` group of `rules.yaml` with warning severity. Acceptance: the v1 reference and
   the worked examples give 0 warnings, and one seeded violation per rule is caught. List any
   check that rule-engine cannot express and what it needs (a resolver, a custom function).
8. **Annotator reference** (D2 §7.5, §10.10, A2). Generate it from `SchemaView`: entity types with
   identity slots, every predicate with its role, modality and condition rule, qualifiers, enums,
   exact value and node shapes, and the worked examples. Compare it with S0-R2's `reference.md`
   section by section and list every difference in information (not wording). Measure its size
   in tokens with the Qwen3.5 tokenizer.

## How to interpret

| Finding | Reading |
|---|---|
| All compile, the v1 batches validate, rules type-check | D2 §7 confirmed; the compilers become the P0.4 specification |
| LinkML loses list annotations | Store lists as YAML strings in annotations, or move them to a sidecar file; `OPEN-D2-6` closed either way |
| The per-predicate `oneOf` is too heavy for the structured-output backend | Emit a flatter model-facing schema (predicate as an enum, qualifiers as a permissive object) and validate predicate-specific rules after generation |
| Custom functions do not type-check in rule-engine | Use resolver-backed attributes (`claim.family_params`); `OPEN-D2-3` closed |
| Every `s0r2_rules.py` check compiles as a `guideline:` warning | The guideline warnings live in `rules.yaml`; the P0.4 warning-rules step ports no Python |
| The generated reference carries the same information as S0-R2's | The reference compiler is specified; the information S0-R2 added by hand that the schema lacks becomes `ci:` annotations or schema text |
| The generated reference exceeds about 1,500 tokens | Filter it by statement kind as D4 §4.2 allows |
