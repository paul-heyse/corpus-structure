## Consequential corrections and evidence

### Subject, enforcement and numerical meaning

`semantic/data_operation_source_discovery.py:42,57` still branches on the literal
`original-source-view`; `EffectiveOperation` carries textual subject/applicability/invariants/
coverage/precision/behavior and hashes several of them (`data_operation_model.py:338–423`).
`data_operation_compilation.py:1660–1664` structures these as strings. That supports the need for
checked domain references, but not replacing every invariant with a binding predicate: schema,
scientific algorithm and native admission constraints have legitimate distinct enforcement owners.
Derive discovery facts from declared relations where possible before adding independent flags.

The numerical concern is narrower than a missing mechanism. `python_operation_sources.py:1099–1145`
already incorporates opaque reference/contract/role/content digest and records unknown revision.
`clause_products.py:42–52` supplies a versioned file capture used by the declaration’s opaque/asset
contracts. Neither establishes that every numerical dependency is represented, nor proves automatic
invalidation on all distribution changes. The integrated review preserves per-operation adequacy
investigation and rejects both label-only policy and indiscriminate whole-environment recipe salts.
Behavior remains a real revision for operations without admitted implementation slices.

### Lifecycle completeness without false exhaustiveness

`change_impact.py:115–123,169–298` uses a string fate and an ordered decision chain; failed/partial/
invalid and several other visible fates lack deliberate branches, while unavailable is listed after
an earlier branch catches it. The generated fate vocabulary exists in `_data_operation_fates.py`.
A dictionary annotated with literal keys permits a subset: it constrains key values, not key presence.
The replacement needs an exhaustive discriminator or exact-key conformance, with independent expected
meaning for each class. Population, native admission and revocation priority remain separate evidence.
No new outcome mapping may silently depend on a historical-definition fallback in the final target.

### Shared preparation is not interchangeable preparation

`data_operation_prepared_call.py:28–166` already centralizes signature/verification/ingress/CPU
completion. Clause and definition repeat physical CPU-plan work; structural acquisition requires one
governing hydrated selection and binds project (`declared_structural_calls.py:482–510`), while
`contextual_encoder.py:364–432` authenticates frame/model custody and builds actual query contexts.
The shared capability should not hide those distinctions behind arbitrary configuration.

Factory module digests enter capabilities (`data_operation_compilation.py:1500–1522`); capabilities
enter definition identity (`data_operation_model.py:430–448`), and implementation slices affect
recipes (`data_operation_compilation.py:1845–1859`). A sound refactor may therefore change identities.
Preserving semantic behavior is the obligation; preserving wrapper code to retain hashes is not.

### Rich standing correction and actual migration burden

The original statement that candidate standing was a docstring is false in the reviewed baseline.
`model/semantic/data-operation-candidate-inspection.yaml:48` requires the exact private standing;
`declared_candidate_products.py:135–144` emits/validates it; reading resolution and finite
interpretation check it. The integrated review removes that diagnosis and retains a genuine need
for complete rich subject/evidence/policy/standing/admission contracts.

`domain_operations.py:848–902,1369–1420` still acquires run/task/input-cut custody and projects
AgentStoredBatch/NativeProposalFrame. DDO `CutSelection` is a pinned read selection, not an already
complete replacement for rich alternatives, known facts, policy and source interpretation. Require
private, accepted-admission and missing/ambiguous-evidence design scenarios. No provider/standing
change is executed here.

`compare_semantic_releases` opens the old execution model (`operation_reporting.py:784–807`), with
actual model/schema CLI and MCP callers. Preserve useful model-difference capability through a target
replacement or retire it explicitly; do not merge it into subject-relative change classification.

The broader acquisition test already exists (`test_downstream_profile_acquisition.py:77–112`). Its
independently expected population and family-specific expectations are valuable controls, not
mechanism duplication. Captured-source/refusal/custody tests survive replacement where they still
assess current guarantees.

## Net design and plan implications

I09 replaces preservation-led adoption with target-native import/regeneration plus complete legacy
code retirement. It covers recently added historical readers as well as older execution architecture.
Prior effort and retained generated data do not establish an exception. Conversion must not invent
provenance, successful effects, knowledge standing or request/derivation/support custody. A structurally
convertible old judgment may still be invalid for a changed question/input basis. Finite conversion
tooling has a removal boundary and is absent from ordinary target execution/serving.

The existing preservation companion and ADR-0095 conflict with this direction and need subsequent
plan/decision revision. Reconcile affected clauses in ADR-0092/0098/0105/0107/0108 and architectural
owners without discarding unrelated identity, native trust, graph or recovery decisions. Neither a
mandatory data reset nor an exhaustive migration before code retirement is recommended. The exact
physical baseline/forward route remains a named plan-preparation decision, based on actual schema
and useful import populations; no database operation is authorized by this review.

A universal payload-schema rewrite remains separate, but the subject, rich evidence/policy/cut and
variant associations needed to make I01/I05/I06 meaningful cannot be deferred as merely untyped
payload cleanup. I07 improves navigation without creating another progress authority. The principal
review now presents I01–I09 as one coordinated amendment, with code-retirement endpoints, deliberate
identity changes and independently discriminating acceptance scenarios.

Accepted implementation status remains exclusively in the DDO coordinator. This audit does not
reopen or close F01–F14/C1–C7/CA findings, adopt recommendations, or restructure that plan. Benefits
remain Proposed and unmeasured. Later plan revision must select the concrete amendments, reconcile
the decision records and retain exact source/context limits of prior receipts.
